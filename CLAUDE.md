## What this is

A construction-firm ordering & delivery prototype ("SiteStock"). A **Worker** on site searches a materials catalog and requests an order; the community **Owner** approves or rejects it (if the community requires approval — configurable); a **Buyer** (owner-granted only) purchases it externally and confirms with a 3-second hold; an approved **Driver** claims it from the pool, collects it from the chosen stockist, and delivers it. Communities work like Discord servers — an Owner creates one, Workers/Drivers join it (by browsing or invite code, subject to Owner approval) — and everything (orders, requests, roles) is scoped to one community at a time.

This started as a **prototype with no backend**. **As of Phase 8B, identity/companies/sites moved to real Supabase** (Postgres + Auth + RLS), **as of Phase 8C, orders/order events/cancellation requests moved too**, and **as of Phase 8D.1, notifications/notification preferences moved too** — all of that data is now shared server-side, RLS-enforced, with concurrency-safe writes via `SECURITY DEFINER` RPC functions. Only two genuinely UI-only session pointers (active community id, active role) — never meant to be shared data — remain `localStorage`. **As of Phase 8D.2, Supabase Realtime exists** (`public/js/realtime.js`) as a freshness-signal layer on top of all of the above — implemented and verified against **the local Supabase stack, the hosted `sitestock-dev` project, and now a genuine second-physical-device (PC + phone) acceptance test, all three passed** (migration `0016` applied to both backends, full test matrix re-run and passed on hosted: notifications, order lifecycle, the two permission-invalidation DELETE scenarios, channel lifecycle, forged-subscription/RLS isolation, disconnect/reconnect). **Phase 8D.2 is closed.** The real-device pass did surface one real bug first — a Worker already inside a site (not sitting on the site picker) didn't get kicked out when the Owner removed their site membership mid-session, until `site.js`'s `subscribeSites` reactive handler was fixed to also re-validate the Worker's currently-selected site against the freshly refreshed, authoritative site cache (see "Phase 8B/8C — hybrid backend state" below and `supabase/README.md`'s Phase 8D.2 section for the full story). Don't casually say "SiteStock has no backend" or "SiteStock is fully multi-device" (both wrong — identity/companies/sites/orders/notifications are all real, RLS-enforced Postgres now, and Realtime is now real-device-proven too).

## Tech stack

- Plain HTML/CSS/JS. No framework, no build step, no bundler, no npm dependencies (no `package.json`, no `node_modules` — Node still isn't installed, see below).
- JS is native ES modules (`<script type="module">`), loaded directly by the browser — no transpilation. The one exception is `public/js/supabaseClient.js`, which imports the Supabase JS SDK straight from `esm.sh` (a plain browser ES module import over the network, the SDK's own documented buildless usage path — not a build-time dependency, not npm).
- State persistence: identity/companies/sites (Phase 8B), orders/order events/cancellation requests (Phase 8C), and notifications/notification preferences (Phase 8D.1) are all Supabase-backed (real Postgres, RLS-enforced — see "Phase 8B/8C — hybrid backend state" below). Only two UI-only session pointers (active community/role — never real data) remain `localStorage`. All of it is wrapped in small pub-sub data modules (see Architecture); as of Phase 8D.2, `public/js/realtime.js` triggers those same modules' existing refresh functions on relevant database changes (verified local, hosted, and real-device — see below).
- Styling is one hand-written stylesheet, no CSS framework.

### Running it

Node is **not installed** on this machine — do not reach for it. The dev server is Python:

```bash
python "dev_server.py"
```

`dev_server.py` is a tiny custom static file server (stdlib `http.server`, no dependencies) that serves `public/` on port 3000 **with caching disabled** (`Cache-Control: no-store`). This replaced a plain `python -m http.server` after a real bug: the plain version served stale files after edits (browsers cache-validated against `Last-Modified` and got incorrect 304s within the same second as an edit). Always use `dev_server.py`, never the plain module.

`.claude/launch.json` is already wired to run this via the `preview_start` tool with name `"buyer-replacement"`. It has `"autoPort": true`, and `dev_server.py` reads `PORT` from the environment (falling back to 3000) — needed because this project sometimes gets opened in more than one chat session at once, and the second one can't bind port 3000. Don't hardcode port 3000 anywhere else; always let the tool tell you which port it actually started on.

### The Browser-pane screenshot tool

`computer{action:"screenshot"}` only works if the user has the Browser pane actually open/focused on their end (they click an "Open SiteStock..." affordance in their UI). If it times out with "the Browser pane is not displayed," that's not a bug to fix — just ask the user to open the pane and retry. Text-based verification (`get_page_text`, `javascript_tool`, `read_console_messages`) always works regardless and should be the default way to verify changes; reach for screenshots only when the user explicitly wants to *see* something visual.

## Architecture

### Three layers, by file

**Data layer** (no DOM access, pure state + pub-sub; Supabase-backed modules add a sync-facade-over-async-cache layer, see "Phase 8B/8C — hybrid backend state"):
- `public/js/orderLifecycle.js` — **rewritten in Phase 8C** as the single async facade for every order-lifecycle action, absorbing what used to be two separate modules — `store.js` (low-level order CRUD) and `cancellationRequests.js` (the cancellation-request collection) — **both deleted**, their responsibilities folded in here. Backed by real `orders`/`order_events`/`cancellation_requests` Postgres tables (RLS-enforced, `SECURITY DEFINER` RPC functions — see `supabase/migrations/0010_order_lifecycle_functions.sql`/`0012_widen_edit_order.sql`), following the same synchronous-facade-over-async-cache pattern `community.js`/`sites.js` established in Phase 8B: reads (`getOrders`, `getOrderEvents`, `getEventsForCommunity`, the cancellation-request reads) stay **synchronous** over an in-memory cache; every write (`createOrder`, `editOrder`, `cancelOrderDirect`, `requestCancellation`, `decideCancellationRequest`, `approveOrder`, `rejectOrder`, `revertApproval`, `startPurchase`, `abandonPurchase`, `completePurchase`, `claimDelivery`, `collectDelivery`, `cancelDelivery`, `deliverOrder`) is genuinely `async`, calling a server-side RPC. **Actor identity is no longer passed in by the caller** — every write derives the acting user from the real Supabase session server-side (`auth.uid()`), so signatures dropped their old `actorId`/`actorName` parameters entirely (e.g. `editOrder(orderId, fields)`, not `editOrder(orderId, fields, actorId, actorName)`). **Since Phase 8D.1, this module no longer calls `notifications.js` at all** — every order-lifecycle notification is written server-side, inside the same RPC transaction as the state change itself (see "Notification system" below). See "Order lifecycle" and "Worker corrections & cancellation" below, and "Phase 8B/8C — hybrid backend state" for the cache-lifecycle and concurrency rules.
- `public/js/community.js` — **Supabase-backed since Phase 8B** (real `communities`/`community_memberships`/`owner_grants`/`buyer_grants`/`buyer_requests` tables, RLS-enforced): communities, membership, join requests, owner grants, buyer grants/requests, the per-community approval-required setting. Also still owns two genuinely local, UI-only pointers — active community id/active role (never retired to Supabase, never security-relevant). Every read function (`isOwner`, `isApprovedMember`, `isBuyer`, `getOwnerIds`, `getBuyerIds`, `approvedMembers`, etc.) stays **synchronous**, backed by an in-memory cache kept fresh by real async Supabase traffic — see "Phase 8B/8C — hybrid backend state" below for why and its cache-lifecycle rules before touching this file. All keyed by user id — see `identity.js`. Buyer-role actions here call one of the seven `notify_*` RPCs (see "Notification system" below) immediately after their own already-authorized direct table write succeeds — since Phase 8D.1, not a client-side notification write. **Since migration `0022`, `decideJoinRequest` no longer does a direct `community_memberships` UPDATE either** — it calls the guarded `decide_join_request` SECURITY DEFINER RPC (state-machine guard + applicant notification in one transaction); the old `community_memberships_decide_owner_only` UPDATE policy was dropped, so there is no direct-UPDATE path left on that table, mirroring `orders`. See "Join-request decision notifications (migration 0022)" below.
- `public/js/sites.js` — **Supabase-backed since Phase 8B** (real `sites`/`site_memberships` tables, RLS-enforced): sites (job locations) within a community, site membership (who's assigned to which site), and the site permission composites (`canAccessSite`, `canCreateOrderForSite`, `canPurchaseForSite`) — same synchronous-facade-over-async-cache pattern as `community.js`. See "Site model" and "Phase 8B/8C — hybrid backend state" below. Not to be confused with `site.js` (singular) below, which is the Worker view — a pre-existing name that predates this module; see that section for why they coexist.
- `public/js/notifications.js` — **Supabase-backed since Phase 8D.1** (real `notifications`/`notification_preferences` tables, RLS-enforced — see `supabase/migrations/0007_notifications.sql`/`0009_rls_policies.sql`/`0014_notifications_backend.sql`), following the same synchronous-facade-over-async-cache pattern every other data module uses: reads (`getNotificationsFor`, `getUnreadCount`, `getPreferences`) stay **synchronous** over an in-memory cache; writes (`markRead`, `markUnread`, `markAllRead`, `savePreferences`) are genuinely `async`. **There is no client-side notification-creation function anymore** — no `notifyUsers` export exists; every notification is created server-side (see "Notification system" below for the three creation paths). See that section for the full architecture.
- `public/js/auth.js` — **rewritten in Phase 8B**: real Supabase Auth (email + password), no longer a local plaintext-password account list. Owns Supabase session state only (no profile data) — see "Phase 8B/8C — hybrid backend state" below. "Skip for now" / anonymous guest mode was **removed entirely** in Phase 8B; an account is now required.
- `public/js/supabaseClient.js` — **new in Phase 8B**. The only place the Supabase JS client is instantiated. Every other module that needs Supabase imports `supabase` from here.
- `public/js/identity.js` — resolves "who is the current user"; the only source of truth for permission-relevant identity (see "Identity model" below). **Rewritten in Phase 8B**: no more anonymous guest sessions (removed along with "Skip for now") — `getCurrentUserId`/`getCurrentDisplayName` read the live Supabase session directly; `resolveDisplayName(userId)` for *other* users stays synchronous over a `profiles`-table cache (see "Phase 8B/8C — hybrid backend state" below).
- `public/js/data.js` — static mock **product** catalog (`PRODUCTS`, `searchProducts`, `getProduct`, `getAvailability`) + pure helpers (`formatPrice`, `getInitials`, `getCategoryIcon`, `timeAgo`). **As of Phase B, no longer owns supplier/branch data** — `BRANCHES`/`getBranch`/`getBranchesForProduct` moved to `suppliers.js`; this file keeps only the literal `ALL_BRANCH_IDS` catalogue-key list (`'b1'..'b12'`) that `PRODUCTS[].branchIds` still references.
- `public/js/suppliers.js` — **new in Phase B**, Supabase-backed (real `suppliers`/`supplier_branches` tables, RLS-enforced global reference data — see `supabase/migrations/0017_supplier_branch_foundation.sql`), same synchronous-facade-over-async-cache pattern every other data module uses: `getSuppliers`/`getSupplierBranches`/`getBranch`/`getBranchesForProduct` stay **synchronous** over an in-memory cache; `refreshSupplierCache()` is the only async write path (there is no create/update/delete — this is read-only reference data from the app's side, see "Phase B" below). `getBranch`/`getBranchesForProduct` are a drop-in replacement for `data.js`'s old versions — same external shape, same `id` semantics (the stable catalogue key, e.g. `'b1'`, never the new internal Postgres UUID). This is migrated **fixture/demo** data, not merchant-verified — see "Phase B — supplier data foundation" below before assuming otherwise.
- `public/js/geo.js` — UK postcode geocoding via postcodes.io (free, keyless) + haversine distance + browser geolocation

**UI layer** (owns a chunk of DOM, renders from data-layer state, wires its own event listeners):
- `public/js/authView.js` — the login/register screen (real Supabase email+password since Phase 8B; the "Skip for now" option is gone)
- `public/js/communityView.js` — the Communities management screen (create/join-by-code/browse/your-communities/pending-requests)
- `public/js/site.js` — Worker view (**select site** → search → size → details → source → confirm → order history), plus (Phase 7C) editing/cancelling/requesting cancellation of the Worker's own orders — see "Worker corrections & cancellation" below. The filename predates the Phase 4A "Site" domain concept and still refers to the worker's job location in the loose everyday sense (`site-orders-list`, `renderSiteOrders`, etc.) — this was a deliberate decision (see PROGRESS.md Phase 4A) not to rename it, since there's no runtime collision with `sites.js`/`sitesView.js` (different files, different identifiers), only a naming-adjacency a reader should be aware of.
- `public/js/owner.js` — Owner view (dashboard stats, real event-log activity feed, Team/grant panel, join-request approval, buyer-request approval, approval-setting toggle, order approval/status tabs incl. Cancelled, read-only per-order detail/timeline — see "Owner order visibility" and "Worker corrections & cancellation" below)
- `public/js/driver.js` — Driver view (location, Requests/My Deliveries/Completed tabs, claim/collect/deliver/cancel)
- `public/js/buyer.js` — Buyer view (list of orders awaiting purchase with full cost, review detail, press-and-hold-3s Purchased confirmation), plus (Phase 7C) a cancellation-requests panel for approving/rejecting Worker cancellation requests — see "Worker corrections & cancellation" below
- `public/js/sitesView.js` — Sites management screen, owner-only (list active/archived sites, create, site detail with edit/archive/restore, employee assign/remove, per-site order list). See "Site model" below.

Each UI module exports a `refreshXView()` used by `main.js` to force a clean re-render when the user switches context (e.g. re-entering after switching community).

**The five role/screen modules — `site.js`, `owner.js`, `driver.js`, `buyer.js`, `sitesView.js` — are lazy-loaded** (commit `9661b10`), not statically imported by `main.js`. They plus their view-only deps (`orderStatus.js`, `deadline.js`, `geo.js`, `orderThreadView.js`, `deliveryPhotosView.js`) are ~220 KB of the app's JS that a given user only ever needs one or two of, so `main.js` pulls the needed one in via `import()` at the point of navigation (`loadView(path)` — a small promise cache that drops a rejected fetch so a flaky first navigation can retry; `ROLE_VIEW_MODULE` maps role → path). `showRoleView`/`showSitesView` kick the `import()` off concurrently with `refreshDataCaches()` (the slower, network-bound half) and `await` it before revealing the view; a genuine load failure → `alert` + fall back to a safe eagerly-loaded screen. `authView.js`/`communityView.js` stay eager (they're the cold-load entry point). Same-origin `import()` is allowed by the page CSP (`script-src 'self'`). Each lazily-loaded module's top-level side effects (its `subscribeX(render)` hooks, its revert-countdown `setInterval`) run on that first import — which is exactly when its view first matters, since `main.js` always calls `refreshXView()` on entry and the pub-sub convention re-runs each listener immediately on subscribe. `index.html` `modulepreload`s the three biggest always-eager modules (`auth.js`, `community.js`, `orderLifecycle.js`) alongside `main.js`/`supabaseClient.js`/the vendored SDK.

**Transition loading veil** (same commit): every transition leaves the previous screen up while its async work runs (a cache refresh, plus now possibly a role-module fetch), then swaps in the finished view — a dead, feedback-free pause on a slow connection. `beginViewLoading()`/`endViewLoading()` drive `#view-loading` (a dimmed overlay + a small "Loading…" card), shown only once the wait passes ~150 ms (fast transitions never flash it) and then held ≥350 ms (no strobe). They're **refcounted** so nesting (`enterCommunityFlow` → `showRoleView`) shows/clears it once; `guardTransition(fn)` wraps each of the six transition functions (`showRoleView`/`showSitesView`/`showCommunitiesView`/`showProfile`/`showRoleSelect`/`enterCommunityFlow`) in a `try/finally` so the veil clears on every path, including a thrown error. `pointer-events: none` — it's a visual cue only, never a lockout if a transition hangs. **Because of `guardTransition`, those six are now `const name = guardTransition(nameImpl)` pairs, not plain `async function` declarations** — the real body is `nameImpl`; external callers still just call `name()`. The `const`s are safe against hoisting only because every call site is a runtime event handler / `routeFromTop` (invoked from `bootstrap()`), never module-eval-time — keep it that way.

**Orchestrator**:
- `public/js/main.js` — the only module that knows about *all* the views. Owns `showOnly(view)` (toggles `.view.active` across every `<section>`), the topbar (community/profile pills, session bar, account dropdown), and all cross-cutting routing logic (`routeFromTop`, `enterCommunityFlow`, `showAuth/showCommunityPicker/showCommunitiesView/showProfile/showRoleSelect/showRoleView`). If you need to add a new top-level screen, it goes in `main.js`'s `ALL_VIEWS` array and gets a `showX()` function there — don't reinvent view-switching elsewhere.

Pattern to follow: data modules never touch the DOM; UI modules never read/write `localStorage` directly (they call data-module functions); `main.js` never renders content itself, only decides which section is visible and calls the UI modules' `refreshXView()`.

### Pub-sub convention

Every data module exposes `subscribeX(fn)`: adds `fn` to a listener set, **calls `fn()` immediately** on subscribe (so callers don't need a separate initial render), and re-calls every listener on any mutation. Cross-tab sync piggybacks on the native `storage` event (listed explicitly per-key in each module — if you add a new localStorage key to an existing module, add it to that module's `storage` listener too, or cross-tab/other-view updates silently stop working for it).

### Landing page (marketing homepage, 2026-09-14)

A logged-out visitor's actual front door is now `landing-view`, not `auth-view` directly — `routeFromTop()`'s `!isAuthenticated()` branch calls `showLanding()` (password-recovery/MFA-challenge checks earlier in the function are unaffected and still land on `auth-view`). It's a separate ChatGPT/Codex-built marketing project, recolored to this app's real navy/orange/cream palette, merged in as one more `<section class="view">` in the same `index.html` — deliberately not a separate path/domain, since that would risk the hosted Supabase Auth redirect URLs (password reset, email confirmation) that are pinned to specific paths.

- **Files**: `public/css/landing.css` (its stylesheet, mechanically scoped — see below), `public/js/landing.js` (its own in-page "layers" navigation for the See How It Works/Problems pages, loaded `type="module"` specifically so its top-level `const`s can't leak into the shared global scope the app's other classic `<script>` tags use).
- **Every selector in `landing.css` is prefixed `#landing-view`, and every one of its custom properties is renamed `--landing-*`.** Both were load-bearing, not defensive, and the failure mode is subtle enough to repeat if a future edit forgets it: landing's original variable names (`--paper`, `--brown`, `--brown-dark`, `--sand`, `--blue`, `--orange`) were already identical in name *and* light-mode value to this app's own tokens — but the app's dark-mode media query redefines several of those same names, and since a custom property resolves through the one real `:root` regardless of which stylesheet declared it, an unrenamed landing.css would render half-flipped to dark-mode colors on any browser with a dark OS preference. The leak runs the other way too — the app's own bare `h1, h2, h3 { color: var(--navy) }` rule (its global heading style, `style.css`) will win over an unscoped landing heading, since bare-element selectors apply document-wide; `landing.css` ends with an explicit `#landing-view h1, #landing-view h2, #landing-view h3 { color: var(--landing-ink); font-family: var(--landing-sans) }` specifically to close this. If landing.css is ever regenerated from the source project, redo both the `#landing-view` selector prefix and the `--landing-` variable rename — don't just recolor and re-paste.
- **`showOnly()` hides the app's own `.topbar` and lifts `main#app`'s normal 720px panel constraint (`.app-full-bleed`) only while `landing-view` is active** — the landing page brings its own full header and edge-to-edge sections, so both the real topbar and the panel-width constraint would otherwise double up or clip it. `.topbar[hidden] { display: none; }` exists because `.topbar`'s own `display: flex` otherwise beats the browser's default `[hidden]` rule at equal specificity — the exact gotcha the Conventions section below already documents; setting `.hidden = true` on an element with its own `display` rule always needs this pairing, not just for the topbar.
- **`setBackgroundInert()` (`landing.js`) must never query `document.querySelector('main')`/`('footer')` globally — scope to `#landing-view`'s own header/`#landing-main`/footer instead.** Found live 2026-09-14 as a real "the whole overlay is frozen — can't click or scroll anything" bug on every internal page (How it works/Problems/the restored Get Started page): the standalone project's own `<main id="main">` was renamed to `<div id="landing-main">` when it was merged in (to avoid an invalid nested `<main>` inside the app's real `main#app` — see the nested-`<main>` note further down), but `setBackgroundInert` was never updated to match, so a global `'main'` query resolved to `main#app` itself. `#site-layer` (the overlay `setBackgroundInert(true)` is called right before opening) lives inside that same `main#app`, and `inert` disables interaction for an element **and every descendant** — so marking `main#app` inert made the overlay it had just opened completely unresponsive to clicks/scroll/focus while still rendering fine visually (inert has no effect on paint), which is exactly why it looked "frozen" rather than broken. Fixed by scoping the three background regions to `landingViewRoot.querySelector('.site-header')` / `document.getElementById('landing-main')` / `landingViewRoot.querySelector('footer')` — never a bare global element-type query for anything inside `landing-view` again, for the same reason.
- **The "Get Started for Free" info page is back** (`data-page-target="start"`, `pageTitles.start`/`pageDefinitions.start` in `landing.js` — this machinery already existed but was orphaned when every trigger got switched to `data-auth-target` during the initial core-site integration). Every "Get Started for Free"-labelled button *except one* now carries `data-page-target="start"` and opens that info page (built from `#start-page-source` + the `roles`/`faq` sections, same in-page-layer mechanism as "See How It Works"/"Problems We Solve For You") instead of jumping straight to auth — the header nav pill, the hero's primary CTA, the "problems" page's closing CTA, the "how" page's getting-started closing CTA, and the persistent in-layer nav pill shown while browsing any internal page. **The one exception is the CTA button *inside* `#start-page-source` itself** (`.start-page .problem-page-actions button`, added 2026-09-14) — that one still carries `data-auth-target="register"`, so the info page has a real, working way to actually continue to signup. The header's Log In/Create an Account buttons and the hero's inline "Log in" link are unaffected — they've always gone straight to `auth-view` via `data-auth-target`, and still do. The click-delegation on `#landing-view` (`main.js`) turns any `data-auth-target` click into the existing `sitestock:go-to-auth` window event (`{ tab: 'register' | 'login' }`), which opens the real `auth-view` on the matching tab; `data-page-target` clicks are handled entirely inside `landing.js`, never reaching `main.js` at all.
- **A `data-auth-target` click must always close the internal-page overlay too, not just open `auth-view`.** Real bug, found live 2026-09-14 (reported as "I can click things but can't scroll" on the *authenticated app*, after login): the new CTA inside `#start-page-source` (previous bullet) is a `data-auth-target` button that lives *inside* the site-layer overlay, so clicking it went straight to `sitestock:go-to-auth` without ever calling `closeInternalPage()`. `body.layer-open` (landing.css: `overflow:hidden`) was left permanently stuck — `main.js` has no idea that class exists, so nothing ever cleared it, and the entire rest of the session (the auth form, then the whole authenticated app after login) lost the ability to scroll. Fixed two ways, deliberately redundant: `landing.js` now closes the overlay on *any* `data-auth-target` click, document-wide, mirroring what its own `data-page-target="home"` already did; and `main.js`'s `showOnly()` independently strips `body.layer-open` whenever the view being shown isn't `landing-view`, as a defensive backstop that doesn't depend on `landing.js` getting every future exit path right. If you add another way to leave `landing-view` (a new button, a new event), you don't need to remember this — the `showOnly()` backstop covers it automatically.
- **`landing.css` had one genuinely unscoped rule that broke the app outside `landing-view` entirely: a bare `footer{display:none}`, inherited as-is from the original standalone project's source `styles.css` (its own line 318) and missed by the scoping script that prefixed everything else.** Found live 2026-09-14, reported as "I can't get out of dark mode" — the footer switch was never invisible-but-reachable, it was `display:none` outright, because `.app-footer` (the real app's global footer — legal links, the accessibility statement, the feedback button, the dark-mode switch, e-commerce-required operator identity) never sets its own `display`, so this one bare, zero-specificity rule was the only declaration in the whole cascade that mattered, and it won automatically regardless of source order. It had **zero visible effect inside `landing-view` itself** — a separate, more specific `#landing-view footer{display:grid;...}` rule already overrode it there, which is exactly why this went unnoticed through every earlier verification pass this same day (all of which looked at `landing-view`, never at the footer on `auth-view` or a logged-in screen). Fixed by scoping it to `#landing-view footer{display:none}` like everything else — a no-op change inside `landing-view` (still overridden there), and the actual fix everywhere else. **If `landing.css` is ever regenerated from the source project again, grep the fresh output for any bare, unscoped selector before trusting it** — the scoping script's own header comment already warns about this class of miss (two similar edge cases were caught and hand-patched at the original merge), but this third one slipped through because it produces no visual symptom at all inside the one view anyone was actually looking at.
- **Password/text inputs need an explicit `color`, not just `background`.** Real bug, found live 2026-09-14 alongside the two above: `.search-input`/`.text-input` (and the two driver/worker header input variants) set `background: var(--sink)` but never `color` — form controls don't inherit `color` from `body` via the UA stylesheet the way ordinary text does, so they were rendering at the browser's own default input text color regardless of theme. Harmless in light mode (default text color is dark, background is light), but in dark mode the background flips to `--sink`'s near-black dark value while the text stayed dark too — a password field a user literally cannot read while typing. Fixed with an explicit `color: var(--text)` alongside `background` in the same override rule (`style.css`'s "Inputs" block). Any new input-like control added to this file needs both properties set explicitly for the same reason — never rely on inheritance for a form control's text color.

### View flow (who can reach what)

```
auth-view (login/register)
  → community-view (front page: name + Log in/Show profile + Go to Communities)
      → communities-view (create / join-by-code / browse / your communities / pending requests)
          → role-select-view (fallback only — see below)
              → worker-view | owner-view | driver-view | buyer-view
                  → sites-view (owner-only, reached via the "Sites" topbar pill — see "Site model" below)
      → profile-view (account details + community memberships + buyer-access request + log out)
```

**Role resolution has no per-visit prompt for real accounts, and — since Phase 8E — a real, reachable switcher for accounts with more than one legitimate role.** At signup, an account answers "worker/driver/buyer/owner" once (`account.defaultRole`, sourced from the session's own `user_metadata.default_role` — **note the snake_case column name**: `auth.js`'s `accountFromSession` reads `user_metadata?.default_role`, matching exactly what `createAccount()` writes at signup. Any test/seed tooling that creates accounts by calling Supabase Auth directly, rather than through the real signup form, must use this exact key — a Phase 8C.5 test-account script that used `defaultRole` (camelCase) instead produced accounts that silently landed on `role-select-view` every time, which was mistakenly reported as an app bug during that session's live-device verification before being traced back to the script itself. This is a live landmine for future test tooling, not a defect in `auth.js`.).

Entering any community calls `resolveEntryRole(communityId, userId, preferredRole)` (`community.js`), rewritten in Phase 8E to make every rule explicit rather than incidental:
1. Owner (creator, or granted — see below) always wins, unconditionally, no matter what they picked at signup.
2. Otherwise, if `eligibleRoles(communityId, userId)` has exactly one entry, enter it directly — no ambiguity to resolve.
3. Otherwise, if `preferredRole` is one of the eligible roles, enter that.
4. Otherwise, if the only ambiguity is worker+driver (always granted together — see below), default to worker, matching long-standing precedent.
5. Otherwise (genuinely ambiguous — e.g. buyer plus worker/driver with no matching preference) return `null`, and the caller (`main.js`'s `enterCommunityFlow`) shows `role-select-view` instead of guessing.

**`role-select-view` ("Choose your role") is reached two ways now, not one**: as the fallback above when resolution is genuinely ambiguous, and — since Phase 8E — as a deliberate **role switcher**, reached via the topbar Menu's "Switch role" (`menuSwitchRoleBtn`). That button's visibility is `eligibleRoles(communityId, userId).length > 1` — **not** "does this account lack a `defaultRole`", which was the pre-Phase-8E condition and was a real, shipped bug: since every real account has a mandatory `defaultRole` since Phase 8B (no more "Skip for now"), that old condition hid the button for 100% of real accounts, permanently, regardless of how many roles they actually had. An **Owner is always also an approved member of their own community** (`isApprovedMember` returns true for `status === 'owner'`), so `eligibleRoles` for a plain owner is `['owner', 'worker', 'driver']`, not just `['owner']` — owners have always been switchable to worker/driver, that capability was just unreachable before this fix. Switching never touches `defaultRole`, memberships, or grants — it only calls `setActiveRole(role)` (a `localStorage` UI pointer, see below) and re-routes; the server-side permission check for whatever the switched-to role then tries to do is entirely independent and re-verified fresh regardless of what the switcher showed. Don't remove `role-select-view` or gate `menuSwitchRoleBtn` on `defaultRole` again — both are load-bearing for this.

### Identity model

**Rewritten in Phase 8B.** `identity.js` resolves "who is the current user" from the live Supabase Auth session — every other module asks it rather than touching session/profile state directly. There is no anonymous/guest identity anymore ("Skip for now" was removed entirely; an account is required).

- `getCurrentUserId()` — the real Supabase `auth.users.id` (a UUID) of the logged-in account, or `null` if unauthenticated.
- `getCurrentDisplayName()` — the current account's `display_name`, read straight from the session's own `user_metadata` (set once at signup) — no extra fetch needed for your own name.
- `resolveDisplayName(userId)` — looks up *another* user's display name, synchronously, from an in-memory cache backed by the `profiles` table (real Postgres, `select`-readable by any authenticated user via RLS — see `supabase/migrations/0009_rls_policies.sql`). A cache miss kicks off a background fetch and returns `'Unknown'` in the meantime, same graceful-degradation shape the old guest-lookup fallback used; the next render (triggered once the fetch resolves) shows the real name. `community.js`/`sites.js` also proactively bulk-prime this cache on their own cache loads, so the common case (an already-known member) never shows the placeholder at all.

**All permission/ownership checks in `community.js`/`sites.js` are keyed by `userId`, never by display name.** This is unchanged from before Phase 8B and just as important now: display names are cosmetic labels only. Order records (`orderLifecycle.js`, Supabase-backed since Phase 8C) keep both: an `*Id` field for logic (`requestedById`, `driverId`, `approvedById`, `rejectedById`) and a parallel display-name string snapshot (`requestedBy`, `driver`, `approvedBy`, `rejectedBy`) taken at the time of the action, so historical order cards still read correctly even if a display name changes later.

### Owner permission model

- `isCreator(communityId, userId)` — true only for whoever's id matches `community.ownerId` (`communities.owner_id` in Supabase — set once at creation, never changes).
- `hasOwnerGrant(communityId, userId)` — true if the creator has explicitly granted this user owner access. **Supabase-backed since Phase 8B** (`owner_grants` table, RLS: only the true creator may insert/delete a row — see `supabase/migrations/0009_rls_policies.sql`).
- `isOwner(communityId, userId)` = `isCreator(...) || hasOwnerGrant(...)`. This is the function almost everything else should call — `isCreator` is only for gating the "Team" grant/revoke UI itself (only the true creator can grant/revoke; a granted owner cannot grant further). Synchronous, cache-backed — see "Phase 8B/8C — hybrid backend state" below.
- Granting fires a one-time "You've been upgraded to owner level" popup for the *recipient's* browser session, tracked via the still-local `sitestock_seen_grants_v1` (a UI "have I shown this" flag, not real data — deliberately not moved to Supabase) so it never repeats (see `findUnseenGrantFor`/`markGrantSeen` in `community.js`, wired in `main.js`'s `checkForNewOwnerGrant`).

### Buyer permission model

Unlike worker/driver (bundled free with approved membership), **buyer access is owner-granted only** — `isBuyer(communityId, userId)` = `hasBuyerGrant(...)`, mirroring the owner-grant shape exactly (**Supabase-backed since Phase 8B**, `buyer_grants` table). This is deliberate: buyer handles real purchasing/financial responsibility, so it shouldn't be automatic. Two ways in: an approved member requests it (`requestBuyerRole`, surfaced on the Profile screen), and any owner (not just the creator — this one isn't creator-restricted) approves/declines via the Team-adjacent "Buyer access requests" panel in `owner.js`; or an owner grants it directly from the Team panel without a request. `buyerRequestStatus(communityId, userId)` returns `'none' | 'pending' | 'granted'` for the Profile UI.

### Site model (Phase 4A)

A **Site** is an individual job location (e.g. "24 High Street") that belongs to exactly one community — a company can have many. Sites live in `sites.js`, following the exact same module shape as `community.js`: its own pub-sub (`subscribeSites`), and — **since Phase 8B** — its own real Postgres tables instead of its own localStorage keys (see "Phase 8B/8C — hybrid backend state" below for the cache-facade pattern this module now uses).

- **Storage**: `sites` and `site_memberships` tables (real Postgres, RLS-enforced — see `supabase/migrations/0004_sites.sql`/`0009_rls_policies.sql`); many-to-many (a site can have any number of employees, an employee can belong to any number of sites; neither side ever assumes 1:1).
- **Ownership/CRUD**: `createSite`/`updateSite`/`archiveSite`/`restoreSite` are all owner-only (`isOwner(communityId, actorId)`, reused from `community.js` — not reinvented) and, since Phase 8B, genuinely `async` (real Supabase writes, RLS-checked server-side too). No permanent delete — see the archive note below.
- **Membership**: `addSiteMember`/`removeSiteMember` are owner-only, `async` since Phase 8B, and require the target user to already be an approved community member (`isApprovedMember`) — site membership is a *further restriction inside* company membership, never a substitute for it.
- **Permission composites** — the only functions anything outside `sites.js` should use to decide "can this user do X with this site":
  - `canManageSite(communityId, userId)` — owner only.
  - `canAccessSite(siteId, communityId, userId)` — owner, or a member of that specific site.
  - `canCreateOrderForSite(siteId, communityId, userId)` — owner, or an approved community member who's *also* a member of that site.
  - `canPurchaseForSite(siteId, communityId, userId)` — owner, or a buyer who's *also* a member of that site.
  
  **Every one of these independently re-derives the site's real `communityId` and refuses if it doesn't match the `communityId` argument** (`siteBelongsToCommunity`, private) — `isSiteMember(siteId, userId)` alone only proves membership of a siteId, not that the site actually belongs to the community being checked against. This was a real gap caught during Phase 4A verification (a caller passing a mismatched `communityId` could otherwise let membership in one company's site satisfy a permission check scoped to a different company) and fixed at the module boundary rather than trusting every call site to pre-validate the pair — same "reference is not permission" discipline as the rest of this codebase. Always call these composites rather than reassembling the logic ad hoc, and always pass `communityId` explicitly — never infer it from `getActiveCommunityId()` inside a permission check, since a user can belong to multiple communities and the active one is session state, not a security boundary.
- **Drivers get no site permission function at all, on purpose.** A driver's access to site info is entirely mediated through order visibility (already gated by `isApprovedMember`, unrelated to sites) — they only ever see the site name/address/postcode/delivery-instructions *snapshot already sitting on an order they can already see*, never a live site record or the site's employee list.
- **Archiving, not deleting.** `status: 'active' | 'archived'` on the site record. Archiving only removes a site from the pickers used to start *new* orders (`getActiveSitesForUser`) — it never touches, blocks, or cancels any order already in flight; the order lifecycle is completely independent of live site status. No permanent-delete function exists.
- **`getActiveSitesForUser(communityId, userId)` has the same owner bypass as the permission composites (Phase 5).** It's the site-picker listing helper behind the worker order-creation flow (`site.js`'s `renderSiteSelectList`) — before Phase 5 it only ever consulted membership rows, so an owner who hadn't separately added themself as a site member couldn't see their own site in that picker, even though `canCreateOrderForSite` already let them create an order for it. That was a real UI/permission mismatch (not a security gap — the data-layer check already allowed it), fixed by returning every active site in the community when the caller `isOwner`, exactly mirroring `canAccessSite`/`canCreateOrderForSite`/`canPurchaseForSite`. A normal (non-owner) worker still needs a real membership row — the bypass only ever applies to an actual owner.
- **Renaming a site never rewrites history.** Every order snapshots `siteName`/`siteAddress`/`sitePostcode`/`siteDeliveryInstructions` once at creation (see Order shape below) — editing or archiving the live site record afterward never changes how a past order reads.

### Community → Sites dashboard integration (Phase 8E)

Real-device testing (two genuinely separate physical devices against the hosted `sitestock-dev` backend) surfaced a product gap: Sites were reachable only via a standalone topbar "Sites" pill, disconnected from the Owner's actual entry point into a community (the dashboard). Phase 8E didn't change the site/permission data model at all — `sites.js`'s CRUD, permission composites, and RLS are untouched — it added a **read-only summary card** to the Owner dashboard (`owner.js`'s `renderSitesSummary`, backed by `sites.js`'s existing `getActiveSites`/`getSiteMembers`) showing each active site's name, employee count, and open-order count, right where an Owner already lands after entering a community. Clicking a site row, "+ New site", or "Manage all Sites" all dispatch a `sitestock:show-sites` window event (matching the pre-existing cross-module navigation pattern `sitestock:show-profile`/`sitestock:go-to-auth` already used, so `owner.js` never needs to import `main.js`) — `main.js` listens and calls `showSitesView(siteId)`, which `sitesView.js`'s `refreshSitesView(siteId = null)` now accepts to open straight into that site's existing detail view when a valid id is given, or the list otherwise (same deep-link-on-entry shape `owner.js`/`buyer.js` already use for orders from notifications). **All actual site CRUD, member assignment, archive/restore, and per-site order listing still lives exclusively in `sitesView.js`** — the dashboard card is a summary and a set of navigation shortcuts into it, never a second implementation of any of that logic. The standalone "Sites" topbar pill is unchanged and still works exactly as before; the dashboard card is an additional, more discoverable entry point, not a replacement.

Workers still cannot create sites and still see the same "You haven't been assigned to a site yet — ask your owner to add you to one" blocking message when they have zero site assignments (unchanged, `site.js` untouched) — only the surrounding copy on the site-selection screen was clarified (a static `index.html` hint-text change) to make the Community → Site → assignment relationship explicit.

### Phase 8B/8C — hybrid backend state

Identity, companies (communities), and sites moved to real Supabase (Postgres + Auth + RLS) in Phase 8B. **Orders, order events, and cancellation requests moved too, in Phase 8C**, and **notifications/notification preferences moved too, in Phase 8D.1** — same real-backend treatment, same `SECURITY DEFINER` RPC + RLS pattern throughout. There is no longer a localStorage-only data slice in this app at all — the two remaining `localStorage` keys (`sitestock_active_community_id`/`sitestock_active_role`) are UI-only session pointers, never data. Don't say "SiteStock has no backend" (everything is real Postgres now). **As of Phase 8D.2, Realtime is fully verified — local, hosted, and a genuine second-physical-device (PC + phone) acceptance test all passed.** Migration `0016_realtime_publication.sql` is applied to both local and hosted `sitestock-dev`. It's now correct to say "SiteStock has live Realtime, real-device-proven." Full detail, including what was tested, lives in `supabase/README.md`'s "Phase 8B — frontend wiring (hybrid)", "Phase 8C — order lifecycle migration", "Phase 8D.1 — server-backed notifications", and "Phase 8D.2 — Realtime" sections; this is the load-bearing summary for day-to-day work in `public/js/`.

**Why a synchronous facade over an async cache for *reads*, not a full async rewrite:** `orderLifecycle.js` and the owner/buyer/driver/site UI modules (`owner.js`, `buyer.js`, `driver.js`, `site.js`) call `isOwner`/`isApprovedMember`/`isBuyer`/`canAccessSite`/`canCreateOrderForSite`/`canPurchaseForSite`/`getCurrentUserId`/`getCurrentDisplayName`/`resolveDisplayName`/`getOwnerIds`/`getBuyerIds`/`approvedMembers`/`getSite` **synchronously, inline, inside render code** — 33+ call sites across those four UI files. Since a real Supabase call is asynchronous, `identity.js`/`community.js`/`sites.js` do the real async I/O internally but keep exposing the exact same synchronous *read* function signatures as before, backed by an in-memory cache. **Every one of the read functions named above must stay synchronous** — do not `await` them, do not make their call sites `async` on the strength of that alone, and do not add real-time correctness expectations that would require them to be.

**`orderLifecycle.js`'s read functions follow the identical rule** (`getOrders`, `getOrderEvents`, `getEventsForCommunity`, the cancellation-request reads) — synchronous over the order cache, for the exact same reason. **Its *write* functions are different: Phase 8C made them genuinely `async`**, and every call site in `site.js`/`owner.js`/`driver.js`/`buyer.js` was updated to `await` them (with a disabled-button/in-flight guard around each one, so a slow network can't produce a duplicate submission) — this was an explicit, scoped decision for Phase 8C, not an incidental change, and it does not license making the *read* functions (here or in `community.js`/`sites.js`/`identity.js`) async too.

**The cache is never the authorization boundary — RLS is** (`supabase/migrations/0009_rls_policies.sql`, extended for orders in `0010_order_lifecycle_functions.sql`/`0012_widen_edit_order.sql`). A stale cache can at worst show a UI affordance a user is no longer entitled to use; the actual Supabase write is independently re-checked server-side and refused if it should be, regardless of what the client cache said. This was directly verified for identity/companies/sites (see `supabase/README.md`'s Phase 8B section) and again for orders in Phase 8C (a live mid-session permission revocation correctly blocked a subsequent write attempt, refused server-side).

**Concurrency (Phase 8C, orders only)**: every order row carries an integer `version` column. Every write RPC takes an `p_expected_version` parameter, does a `SELECT ... FOR UPDATE` inside the function, and refuses with Postgres error code `40001` (serialization_failure) if the row's real version doesn't match what the client last saw — this is real database-level optimistic concurrency, not a client-side "re-read before write" convention the way orders' old localStorage guard worked. **A `40001` from Postgres surfaces as HTTP `500` through PostgREST's default SQLSTATE-class mapping** (class `40` → 500) — this looks alarming in a raw network log but is expected and correctly handled: `orderLifecycle.js`'s `handleRpcFailure` checks `error.code` (the SQLSTATE embedded in the response body, exposed by supabase-js regardless of HTTP status), not the HTTP status, so the stale-version refresh path fires correctly. Don't "fix" this by trying to make the RPC return a different HTTP status — that's a PostgREST platform behavior, not a bug in this codebase.

**Pricing trust boundary (Phase 8C, be upfront about this)**: `total_price` is always server-computed (`unit_price × quantity`, inside the RPC — the browser can never set it directly), and `unit_price` is validated server-side as a sensible non-negative numeric value. **There is no server-side product catalogue** — `unit_price` itself still comes from the browser's `data.js` mock catalog, so while the arithmetic and non-negativity are enforced server-side, the *price itself* is still client-asserted, same trust level as before Phase 8C. Don't describe pricing as "server-trusted" or "supplier-verified" — say specifically that the computation is server-enforced but the input price is not, until a real supplier/product-catalogue integration exists (not scoped, not started).

**Cache lifecycle** — read this before adding a new mutating function to `community.js`/`sites.js`/`identity.js`/`orderLifecycle.js`:
- Refresh on login/logout: `community.js`/`sites.js` each `subscribeAuth(() => refresh...Cache())` internally. **`subscribeAuth(fn)` calls `fn()` immediately at subscribe time** (same "call it once on subscribe" pub-sub convention as every other module here) — which runs at `community.js`'s own module-eval time, before `auth.js`'s `authReady` (an async `supabase.auth.getSession()` call) has resolved even once. A real bug, found live 2026-09-16: that premature call saw no user yet, took `refreshCommunityCache()`'s "no user" branch, and permanently marked the cache `communityCacheReady = true` with an *empty* community list — so `main.js`'s own live membership-revalidation handler (below) saw that empty-but-"ready" state and cleared the active company before the real fetch moments later ever got a chance to confirm the user was still a valid member. Every returning session with an already-active company was silently bounced to the picker on load. Fixed by having `refreshCommunityCache()` itself `await authReady` before checking `getCurrentUserId()` (a no-op for every other caller, which only ever runs post-startup) — if you add a new `subscribeAuth`-driven refresh anywhere, give it the same guard rather than assuming auth state is already known just because the callback fired.
- Refresh after every write: mutating functions update the cache from the server's own returned row before resolving — never an optimistic guess. `orderLifecycle.js`'s failure path additionally refreshes the affected order/request (and, on a `42501` permission refusal specifically, the community/site caches too, since a permission failure there often means a grant changed) — see `handleRpcFailure` in that file.
- Explicit async bootstrap in `main.js` (awaits session restore + an initial full cache load, now including `refreshOrderCache()`) before the very first `routeFromTop()` — nothing renders a role view off an empty cache. `index.html`'s `#bootstrap-loading` panel covers the screen meanwhile.
- Refetch on view entry: `main.js`'s routing functions (`showRoleView`, `showRoleSelect`, `enterCommunityFlow`, `showCommunitiesView`, `showSitesView`, `showProfile`) each `await` a cache refresh (community + site + order) before rendering.
- Refetch on window focus: a lightweight `window.addEventListener('focus', ...)` in `main.js`. Kept as a fallback even after Phase 8D.2 (below), not superseded by it.
- **Supabase Realtime (Phase 8D.2) — implemented and verified: local, hosted, and a genuine second-physical-device (PC + phone) acceptance test, all passed.** `public/js/realtime.js` is a small orchestration module (two channels — one user-scoped for `notifications`, one community-scoped for everything else in the approved table set) that, on any relevant `postgres_changes` event, calls the exact same authoritative `refreshXCache()` functions this whole section already documents — never applies event payloads directly to any cache. See that file's own header for the full design (generation guard, coalescing, reconnect handling) and `supabase/migrations/0016_realtime_publication.sql` for the database side, including a real bug found and fixed during local verification: `owner_grants`/`buyer_grants`/`site_memberships` need `REPLICA IDENTITY FULL`, not Postgres's default, because those are the only three tables anywhere in this codebase where a row is ever genuinely DELETEd (revoke/remove), and a DELETE's WAL entry under DEFAULT identity only carries primary-key columns — a `community_id` channel filter can never match it otherwise, and Realtime silently drops the event rather than erroring. **A second real bug was found during the physical-device acceptance pass itself**: `site.js`'s `subscribeSites` reactive handler only ever re-rendered the site *picker's* list, and only while the Worker was actually sitting on the picker screen — a Worker who had already selected a site and was on the search/order-form screens (`selectedSite` set, picker hidden) kept using that site with no visible change after their membership was removed mid-session, since nothing was checking `selectedSite` against the freshly refreshed cache at all. Fixed by having that same handler also compare `selectedSite` against the authoritative, just-refreshed `getActiveSitesForUser()` result and, if it's no longer in the list, calling the existing `refreshWorkerView()` to force the Worker back to a safe, freshly re-derived site-selection state — never trusting the raw Realtime payload, and never replacing `createOrder`'s/`editOrder`'s own independent server-side `canCreateOrderForSite` re-check, which was never bypassable and was never the actual security boundary here. All of the mechanisms listed above this bullet remain fully in place and load-bearing — Realtime is additive, not a replacement; the app must and does still work correctly with the websocket unavailable.

### Order lifecycle

The order state machine and its append-only event log both live in `orderLifecycle.js` — **UI code must never bypass its guarded async functions for a lifecycle action** (there is no lower-level order-write module to fall back to since Phase 8C — `store.js` no longer exists). Every transition goes through a guarded function there (`approveOrder`, `rejectOrder`, `revertApproval`, `startPurchase`, `abandonPurchase`, `completePurchase`, `claimDelivery`, `collectDelivery`, `cancelDelivery`, `deliverOrder`), each now a real async call to a `SECURITY DEFINER` Postgres RPC (`supabase/migrations/0010_order_lifecycle_functions.sql`) that re-reads the order fresh under a row lock, checks the transition is legal from its *current* status and expected `version` (and, where relevant, that the actor is actually allowed — e.g. only the assigned driver can collect/cancel/deliver their own claim, enforced by `auth.uid()` server-side, not a passed-in id), applies the patch, and appends one or more events, all in one transaction. An invalid call is refused with `{ ok: false, error }` regardless of what the UI happened to render — this is now enforced by real database constraints and RLS, not just client-side JS, so invalid transitions are structurally impossible even from a direct unauthorized API call, not just hidden by the UI.

```
pending_approval ──approve──▶ pending_purchase ──start_purchase──▶ purchase_in_progress
       │                            ▲  │                                  │
     reject                         │  └──revert (within 72h)─────────────┘
       ▼                            │                              complete_purchase │ abandon_purchase
   rejected ───revert (within 72h)──┘                                     ▼
                                                                       purchased ◀──────────────┐
                                                                           │ claim               │
                                                                           ▼                      │
                                                                       claimed ──cancel (reason)──┘
                                                                           │ collect
                                                                           ▼
                                                                       collected
                                                                           │ deliver
                                                                           ▼
                                                                       delivered
```

- Worker's `site.js` creates an order via `orderLifecycle.createOrder`, which starts it at `pending_approval` or `pending_purchase` depending on the community's `isApprovalRequired()` setting (toggle in `owner.js`, off by default *stays* off for existing orders — each order snapshots `approvalWasRequired` at creation so a later setting change never silently reinterprets it). `createOrder` also independently re-checks `canCreateOrderForSite(siteId, communityId, actorId)` (`sites.js`) before writing anything and refuses with `{ ok: false, error }` if it fails — this is a real data-layer check, not just a UI gate, so a worker can't create an order for a site they aren't assigned to no matter what got rendered. On success it snapshots the site's `name`/`address`/`postcode`/`deliveryInstructions` onto the order (see Order shape below). `startPurchase` has the equivalent check via `canPurchaseForSite`.
- Owner approves/rejects (`pending_approval` only). A decision can be **reverted** within a 72-hour window (`REVERT_WINDOW_MS`, exported from `orderLifecycle.js`) — but only if `approvalWasRequired` is true, and only while the order is still `pending_purchase`/`rejected`. The lock point is `purchased`, not `picked_up`/`collected` as in the old model — once a buyer has actually spent money, reverting the *approval* doesn't undo that, so it stops being offered.
- Buyer reviews (full cost visible), then must **press and hold "Purchased" for 3 real seconds** (`buyer.js`, `pointerdown`/`pointerup` driving `startPurchase`/`completePurchase`/`abandonPurchase`) — the hold is a confirmation that they already paid externally, not SiteStock processing anything. **Since Phase 8C, the countdown itself never starts until `startPurchase` has actually round-tripped to the server and succeeded** — `buyer.js`'s hold state machine (`idle → starting → holding → completing/abandoning → done`) awaits the RPC before entering `holding`; a release requested mid-flight is deferred and handled once the await resolves, never fired twice. The hold itself is a real database state (`purchase_in_progress`, guarded by the same `version` check as every other write), which is what stops two buyers from both confirming the same order at once, exactly like driver claiming below — verified with a genuine two-connection concurrent `start_purchase` race (raw `psql`, not just pgTAP's single-transaction sequencing): exactly one succeeded, the other correctly refused. Buyer hold state resets after a completed purchase via `clearCompletedHold()` at the list/navigation lifecycle boundaries, so subsequent orders in the same session remain usable — previously the terminal `'done'` phase was never reset to `'idle'`, permanently disabling the hold button for the rest of the session after one purchase.
- Driver claims (`purchased → claimed`), collects, then delivers. **Since Phase 8C, the driver double-claim race is closed by a real database row lock + `version` check inside `claim_delivery`**, not a client-side localStorage re-read — verified with a genuine two-connection concurrent claim attempt on the same order: exactly one connection's claim succeeded, the other was refused with a stale-version error. Delivering requires the driver to fill in **when** it was delivered (`deliveryTime`, a datetime-local input) and **where** (`deliveryLocation`, free text, pre-filled with the original delivery postcode but editable) before `orderLifecycle.js`'s `deliverOrder` will accept it — both are required at the data layer (the RPC itself), not just the form. `deliveredAt` is recorded automatically alongside them (system timestamp of confirmation) and is deliberately kept distinct from the driver-reported `deliveryTime`, since they can differ (e.g. confirmed later due to no signal). No photo proof — deliberately out of scope. **Drivers never see `unitPrice`/`totalPrice`** — stripped from `driver.js`'s render entirely, not just unused.
- Driver can **cancel** a claimed (not yet collected) delivery — reason required, order returns to `purchased` (back in the pool), `driver`/`driverId` cleared on the order but preserved in the `delivery_cancelled` event's `meta` (since the order's own fields no longer have it) alongside `purchasedById`, which is exactly what the `delivery_cancelled` notification (see below) uses to tell the buyer who dropped it and why.

### Worker corrections & cancellation (Phase 7B data layer, Phase 7C UI)

A genuine new terminal status, **`cancelled`**, was added to `TRANSITIONS` (distinct from `rejected` — rejected means the Owner said no before purchase, cancelled means the Worker withdrew it, sometimes after money was spent; conflating them would blur exactly the accountability distinction this codebase already goes out of its way to preserve elsewhere). It's reached from three different places, all through one shared action key so the state machine doesn't fork into two "cancelled" flavors:

```
pending_approval ──cancel_order──▶ cancelled ◀──cancel_order── pending_purchase
                                        ▲
                     purchased/claimed ─┘  (cancel_order, Buyer-approved only)
```

- **`editOrder(orderId, fields)`** — a Worker correcting their own order (`requestedById === auth.uid()`, re-checked fresh server-side since Phase 8C rather than via a passed-in `actorId`, no Owner override in this phase). Which action key it hands to the shared transition logic depends on more than status alone, since `pending_purchase` is reached two different ways:
  - `pending_approval`, or `pending_purchase` with `approvedById` still `null` (approval was off for this order) → action `edit`, a same-status transition (nothing's been signed off, nothing to protect).
  - `pending_purchase` with `approvedById` set (a real Owner approval happened) → action `edit_and_reapprove`, which resets status to `pending_approval` **and clears the approval fields in the same patch** — editing an already-approved order can never silently survive as the version the Owner actually signed off on. This reuses the exact `pending_purchase → pending_approval` edge the Owner's own manual revert already used, just Worker-triggered, rather than a second parallel change-request system.
  - `purchase_in_progress` and everything `purchased`-and-beyond: refused outright, before `applyTransition` is ever called.
  - Only a fixed field whitelist (`EDITABLE_ORDER_FIELDS` in `orderLifecycle.js`) is ever accepted from the caller — `requestedBy`/`requestedById`/`createdAt` and every actor/status field are never in it, so a caller can't smuggle a provenance or status change in through the patch. A `siteId` change is authorized exactly like `createOrder` does (`canCreateOrderForSite`, active-site check, community match) and re-snapshots `siteName`/`siteAddress`/`sitePostcode`/`siteDeliveryInstructions` from the *new* site's live record — never trusting caller-supplied site text.
  - Logs **two** events from the one transition when it forces reapproval — `order_edited` (carrying `meta.changes`, a `{ field: { from, to } }` diff of only what actually changed) and `approval_reverted` (the exact existing type, reused) — the same multi-event-per-transition shape `cancelDelivery` already uses (`delivery_cancelled` + `delivery_returned_to_pool`). The original `approved` event from when the Owner first signed off is never touched — events are append-only; this only adds to the record. An edit reusing `order_awaiting_approval` (unchanged type) re-notifies the Owner, since a Worker's edit is genuinely new work for them — unlike the Owner's own revert, which doesn't re-notify since they obviously already know.
- **`cancelOrderDirect(orderId, reason)`** — instant, Worker-initiated, only legal at `pending_approval`/`pending_purchase` (regardless of how `pending_purchase` was reached — the boundary here is *money spent*, not approval, unlike editing). Refuses with a specific, retryable message at `purchase_in_progress` (the Buyer's hold resolves in seconds either way) rather than a generic transition error.
- **Post-purchase, cancellation becomes a request, not a direct action** (`purchased`/`claimed` only — blocked from `collected` onward, since the goods are then physically with the driver and approving a cancellation would need a way to tell them to stop, which this phase deliberately doesn't build). `requestCancellation`/`decideCancellationRequest` in `orderLifecycle.js` manage a real Postgres `cancellation_requests` table (**Supabase-backed since Phase 8C** — the standalone `cancellationRequests.js` module that used to own this as a separate localStorage collection was retired; its responsibilities folded into `orderLifecycle.js`'s own cache/RPC pattern), still following the same request shape `community.js` established for join/buyer requests — a `pending`/`approved`/`rejected` row per request, only one pending request per order at a time (enforced by a real partial-unique constraint server-side now, not just application logic). Every permission check (is this actor the order's requester, is this actor a currently-valid buyer for the site via `canPurchaseForSite`) is re-verified server-side inside the RPC, not just client-side.
  - **`order.status` is left completely untouched while a request is pending** — a Driver can still claim/collect normally; nothing about claiming is gated on whether a request exists. When the Buyer decides, `decideCancellationRequest` re-reads both the request and the order fresh and re-attempts the underlying `cancel_order` transition — which has **no edge at `collected`**, so an order a Driver has since collected refuses *at the table itself*, not via a hand-written status check. On that refusal the request is deterministically auto-closed as `rejected` (with a system-generated `decisionReason`) rather than left dangling as `pending` forever, and a `cancellation_rejected` event is logged — the Worker gets a truthful outcome instead of silence.
  - Approval clears `driver`/`driverId`/`claimedAt` on the order (mirroring how a Driver's own `cancelDelivery` already clears them) while preserving the departing driver's identity in the `order_cancelled` event's `meta` (`previousDriverId`/`previousDriverName`) — and, since the Driver otherwise has no way to learn the thing they claimed is no longer needed, they're added as a recipient of the same `cancellation_approved` notification the Worker gets, not a new notification type.
  - **Only four new event types exist**: `order_edited`, `order_cancelled`, `cancellation_requested`, `cancellation_rejected`. There is deliberately no separate `cancellation_approved` *event* — an approved request's order-level consequence is already fully captured by `order_cancelled` with `meta.via: 'cancellation_request'` (vs. `'direct'`), so a second event for the same instant would be redundant. `cancellation_approved` only exists as a *notification* type.
  - `orderCancelledBy`/`orderCancelledById`/`orderCancelledAt`/`orderCancellationReason` (new, additive order fields, set by either cancellation path) are **deliberately distinct** from the pre-existing `cancelledBy`/`cancelledById`/`cancelledAt`/`cancellationReason`, which mean something different (a Driver dropping their own delivery claim — order stays alive) — reusing those names for the order's own terminal cancellation would quietly conflate two unrelated events.
  - **No `sitestock_orders_v4` version bump** — every new field is additive/nullable, and `cancelled` is just a new value for the existing `status` field, matching the precedent already set for `requireOwnerApproval` and `siteId`. `sitestock_cancellation_requests_v1` is a brand-new collection, same as `sitestock_sites_v1` was in Phase 4A.
- **Worker UI (`site.js`, Phase 7C)**: each of the Worker's own order cards (`order.requestedById === currentUserId`, checked in the UI purely to decide what to *show* — the real gate is always the guarded async function itself, re-checked server-side when a button is actually pressed) gets "Edit order"/"Cancel order" in Zone 1/2, or "Request cancellation" once purchased/claimed, or nothing once a request is already pending (shown instead as "Cancellation requested — awaiting Buyer decision", or "Cancellation rejected: <reason>" if their last request was declined — both derived from `orderLifecycle.js`'s cancellation-request cache, not the raw event log). Direct cancel reuses `buyer.js`'s exact press-and-hold pattern (`.hold-confirm-btn`, 3000ms) but only calls `cancelOrderDirect` once at the *end* of a completed hold — unlike the Buyer's purchase hold, there's no data-layer "in progress" lock to create/abandon partway through, since a direct cancel is a single atomic action. The edit form is one consolidated panel (`editState.mode`: `summary`/`pick-material`/`pick-variant`/`pick-source`/`pick-site`) rather than the full multi-step creation wizard reused as separate screens — deliberately simplified per explicit direction, while still reusing the exact same underlying data (`searchProducts`/`getBranchesForProduct`/`getAvailability`/`getActiveSitesForUser`) and picker markup (`.result-card`/`.variant-list`/`.source-option`) the creation wizard already uses. Changing the site only ever offers `getActiveSitesForUser`'s own list — never free text — so an unauthorized site can't even be selected in the UI, on top of `editOrder`'s own independent re-check. If the edit would invalidate a real Owner approval, a persistent hint ("Changing this order will require the Owner to approve it again") is shown before the Worker can save, not as a second approval system.
- **Buyer UI (`buyer.js`, Phase 7C)**: a "Cancellation requests" panel (hidden when empty, matching the exact show/hide pattern `owner.js`'s join/buyer-request panels already use) lists every `pending` request whose order the current Buyer can act on via `canPurchaseForSite` — the same check `decideCancellationRequest` itself re-runs, so this list is a display convenience only, not an independent permission surface. Approve/Reject both reveal an inline deliberate-confirmation step (reusing the `.reject-form` pattern already used three times elsewhere) rather than a press-and-hold — a cancellation decision is reversible in spirit (nothing's committed until confirmed) the way the Buyer's own purchase-hold isn't, so the lighter pattern is the correct fit, not an inconsistency. A refusal returned by the data layer (e.g. the order was collected before the decision landed) is shown verbatim, never silently treated as success.
- **Owner UI (`owner.js`, Phase 7C)**: a seventh tab, **Cancelled** (`TAB_GROUPS.cancelled = ['cancelled']`), kept deliberately separate from Rejected. `EVENT_RENDER` gained entries for all four Phase 7B event types, including a structured, human-readable diff for `order_edited` (e.g. "quantity 10 → 15, site Site A1 → Site A2" — raw id/sub-fields like `siteId`/`sitePostcode` are filtered out of the summary, though they're still present in the underlying `meta.changes` for anyone reading the raw event) and a rendering fork for `cancellation_rejected` that distinguishes a real Buyer decision from the automatic close-out when a Driver collects an order before anyone decides (`meta.autoClosed`) — the timeline never attributes the auto-close to "the buyer," since no buyer actually acted. `renderOrderCard`'s revert-section branch was given an explicit `cancelled` case (empty, not the generic `renderRevertSection` fallback) specifically because that fallback's "once purchased, orders can't be reverted" message reads as if a purchase happened even when a `cancelled` order never got that far.
- **Notification click-through** needed no `main.js` changes at all — the generic Phase 6 routing already handles any new type/role/orderId combination. The one addition is in `buyer.js` itself: since a `cancellation_requested` notification points at an order that isn't `pending_purchase` (so `refreshBuyerView`'s existing detail-opening path doesn't apply), a small `highlightCancellationRequestForOrder` scrolls/flashes the right row in the new panel instead — the exact same `.order-card-highlight` class and 2000ms timeout `main.js`'s own `highlightOrderIfPending` already uses, just retargeted at this panel.

### Needed-by deadline (Roadmap Step 2)

**Done — local and hosted verified, migration `0019`, 200/200 pgTAP.** Orders now carry two additive, nullable columns: `needed_by_type` (`'asap' | 'deadline' | null`) and `needed_by` (`timestamptz`, only ever non-null when `needed_by_type = 'deadline'`). A database `CHECK` constraint (`orders_needed_by_valid_state`) enforces exactly three legal states — `(null, null)` for historical/unspecified orders, `('asap', null)`, and `('deadline', <real future timestamp>)` — and rejects everything else, including any other type-value string. **`needed_by_type` deliberately never stores `'today'`/`'tomorrow'`/`'custom'`** — those are pure UI shortcuts (`public/js/deadline.js`) that always resolve to a real `'deadline'` timestamp before reaching the database; the timestamp is the only source of truth, so a displayed "Today"/"Tomorrow" label is always computed fresh at render time by comparing the stored timestamp to the current date, never trusted from a frozen type — this is what stops an order created "for tomorrow" from still saying "Tomorrow" once that's no longer true.

- **ASAP is never `now()`.** Storing the creation instant as a deadline would make an ASAP order technically overdue the moment it's created. ASAP is a pure urgency signal with `needed_by` left `null`.
- **Worker UX**: inside the existing order-details step (create) and the existing consolidated edit panel (edit) — no new wizard screen, one shared control (`site.js`'s `renderNeededByControl`/`wireNeededByControl`) used identically by both flows. Four choices: `ASAP` / `Today · by 17:00` / `Tomorrow · by 17:00` / `Choose date & time`. **"Today" is hidden once local time reaches its 17:00 cutoff** — never silently rolled into tomorrow. Today/Tomorrow are both fixed at 17:00 local (a construction-relevant end-of-working-day cutoff, not derived from anything more precise), constructed via `Date#setHours`/`setDate` (DST-safe — verified live against a real BST→UTC conversion) rather than `Date.now() + 24h`. The confirmation screen always shows the resolved "Needed by: …" line before submit.
- **`create_order`/`edit_order` were widened** (18/20/19-arg → see migration `0019`) to accept `p_needed_by_type`/`p_needed_by`, following the exact drop-then-recreate-then-re-grant discipline `0012`/`0013` already established — old signatures explicitly dropped, new signatures explicitly re-granted to `authenticated` only (never `anon`/`public`). `edit_order` only re-validates "must be in the future" when the deadline is **actually changing** (`is distinct from` the row's current stored value) — an unrelated edit (e.g. only quantity) on an order whose existing deadline has since naturally passed remains possible, exactly matching how every other field-level edit-forces-reapproval rule in this codebase already works.
- **Display**: `public/js/deadline.js`'s `formatNeededBy(neededByType, neededByMs)` is the single shared formatter, imported identically by `site.js`/`owner.js`/`buyer.js`/`driver.js` — "ASAP", "Today, 17:00", "Tomorrow, 17:00", "Tue 25 Aug, 15:00" (absolute), or "Not specified" for historical `null`/`null`. Owner (card + detail panel), Buyer (list + review screen), and Driver (Requests/My Deliveries/Completed, via the existing shared `renderOrderCard`) all display it read-only — no new role capability, no Owner override mechanism.
- **No new notification type, no Realtime change.** `orders` was already published; the two new columns ride along on the existing `postgres_changes` → `refreshOrderCache()` path with zero `realtime.js` changes — verified live via a genuine second open tab. The existing `order_awaiting_approval` (creation, and forced-reapproval-after-edit) notification paths are reused unchanged; `0019`'s notification-writing SQL is byte-identical to `0014`'s.
- **Known, accepted nuance**: when only a deadline's *timestamp* changes (e.g. Today → Tomorrow) without its *type* changing, the Owner's human-readable edit-diff summary line reads "needed by deadline → deadline" — technically accurate (the type genuinely didn't change) but not maximally informative. The underlying data, live display, and `meta.changes` full detail are all correct; this is a summary-line wording nuance only, not fixed this phase.
- **Driver zero-price rule is completely unaffected** — re-verified (grep + live) with every change this phase.
- **Deliberately not built this phase**: any "overdue"/"at-risk" logic, weighted/urgency-aware supplier ranking, calendars, recurring orders. See "Things NOT to do without asking" below for the full scope lock.

### Notification system

**Rewritten in Phase 8D.1.** `notifications.js` is a synchronous-facade-over-async-cache module (same pattern as `community.js`/`sites.js`/`orderLifecycle.js`) over two real Postgres tables, `notifications`/`notification_preferences` (RLS-enforced — see `supabase/migrations/0007_notifications.sql`/`0009_rls_policies.sql`/`0014_notifications_backend.sql`). Its exported reads (`getNotificationsFor`, `getUnreadCount`, `getPreferences`) stay synchronous over an in-memory cache; its writes (`markRead`, `markUnread`, `markAllRead`, `savePreferences`) are genuinely `async`, hitting the tables directly (both are already RLS-scoped to `auth.uid()`, so a direct client UPDATE/UPSERT is safe for these operations — see below for why creation is different).

**Notification CREATION is not a client-side operation at all — there is no `notifyUsers` export.** The `notifications` table has no INSERT grant for `authenticated` (deliberately, since 0007's original schema-only migration — "notifications are always a system-generated side effect"), so a raw client insert is refused outright, not just discouraged by convention. Three server-side paths create every notification:
1. **Order-lifecycle notifications** (12 types) are appended inside the existing order-lifecycle RPCs themselves (`supabase/migrations/0010_order_lifecycle_functions.sql`/`0013`/**0014**), in the same transaction as each RPC's own `order_events` insert — content (title/message, including price via a `_format_price` SQL helper matching `formatPrice`'s exact `£X.XX` format, and product/variant labelling via `_order_label`) and recipient lists (owners/buyers/approved members, computed via direct SQL against `owner_grants`/`buyer_grants`/`community_memberships`, mirroring `getOwnerIds`/`getBuyerIds`/`approvedMembers` exactly) are all computed server-side from the row the RPC itself just validated and wrote — never from client input. `orderLifecycle.js` doesn't call `notifications.js` at all anymore; the RPC call for the state change *is* the notification call.
2. **Non-order notifications** (7 types: buyer access grant/revoke/request/reject, site member add/remove, site archive) split across two sub-patterns, revised in the **Phase 8D.1 hardening pass (migration `0015`)** after a pre-commit audit found the original revoke/remove design weaker than the other five:
   - **Grant/request/reject/add/archive (5 types)** stay exactly as 0014 designed them: `community.js`/`sites.js` perform their existing direct client table write first (grants/memberships aren't RPCs), then call one of five narrow `notify_*` RPCs (`notify_buyer_access_granted`, `notify_buyer_access_requested`, `notify_buyer_access_rejected`, `notify_site_member_added`, `notify_site_archived`) immediately after. Each independently re-validates the specific claim against a row that still persists — e.g. `notify_buyer_access_granted(communityId, recipientId)` requires a `buyer_grants` row to actually exist matching `(communityId, recipientId, granted_by_id = auth.uid())`.
   - **Revoke/remove (2 types)** were redesigned in `0015`, because their underlying row is *deleted* by the time a separate notify call would run — there's nothing left to validate the claim against, so the old design could only fall back to "is the caller currently an owner," letting a real owner send a misleading "access removed"/"removed from site" notification for someone who was never actually revoked/removed. **`revoke_buyer_access(communityId, recipientId)` and `remove_site_member(siteId, recipientId)` are now the sole path for these two operations** — each authenticates, verifies owner authority, performs the `DELETE` itself, checks Postgres's own `FOUND` variable (refusing with `42704` if zero rows matched — i.e. the grant/membership never existed), and only then inserts the notification, all in one transaction. `community.js`'s `revokeBuyerAccess`/`sites.js`'s `removeSiteMember` call these RPCs directly instead of doing a client-side delete. The two superseded RPCs (`notify_buyer_access_revoked`, `notify_site_member_removed`) still exist (0014 is never edited) but had their `EXECUTE` grant revoked in `0015` — permanently unreachable by any client, closing the gap outright rather than just adding a better alternative alongside the old one.
   
   A caller cannot forge a notification for a fact that isn't true, for any of the 7 types — verified directly (locally via pgTAP `supabase/tests/06_notification_backend.sql` + `07_notification_matrix.sql`, and against the hosted project) with a stranger attempting a raw `notifications` insert, every `notify_*`/`revoke_buyer_access`/`remove_site_member` RPC for someone else's grant/membership, and — for revoke/remove specifically — a *legitimate owner* attempting to revoke/remove a grant/membership that was never real, all refused (`42501`/`42704`).
3. **The join-request decision** (2 types: `membership_approved`, `membership_declined`), added in migration `0022`. A **third** pattern, distinct from both above: like the order-lifecycle RPCs it's a **guarded state-machine RPC** — `decide_join_request(p_request_id, p_decision)` (SECURITY DEFINER, `grant execute` to `authenticated` only) locks the `community_memberships` row `for update`, enforces `pending → approved|declined` exactly once (`where status = 'pending'` on the UPDATE itself, not a separate SELECT-then-check — so a double-click, a replay, or two competing owner sessions all resolve to one winner + a clean `40001` for everyone else, identical discipline to every order-lifecycle RPC), re-checks `is_owner(community_id, auth.uid())` server-side, and inserts the applicant's notification in the same transaction from the row it just wrote — but unlike path 1 the notification isn't about an order. `community.js`'s `decideJoinRequest` calls this instead of its old direct `.update()`. Approve-time **site assignment stays a separate client step** (`owner.js` still calls `addSiteMember` itself after the RPC resolves `{ ok: true }`, with its own `notify_site_member_added`) — deliberately not folded in, so a site-assignment failure never rolls back a good approval and `addSiteMember`'s own authorization isn't duplicated. `0022` also **dropped the `community_memberships_decide_owner_only` UPDATE policy** (0009): it was only ever a wrapper around the old client update, and once the RPC exists it's a live bypass door — any authenticated owner could still raw-`UPDATE`, skip the pending guard, re-decide a request any number of times, and never trigger a notification. `community_memberships` now has **zero UPDATE policy for `authenticated`**, exactly like `orders`.
- **`notification_type_enabled_for(userId, type)`** (SQL function) is the single source of truth for creation-time preference filtering server-side, mirroring the old client-side `NOTIFICATION_TYPES`/`DEFAULT_PREFS`/`isTypeEnabledFor` exactly (same category/configurable/subKey mapping, same defaults) — every insert above gates through it, so preference semantics didn't change when creation moved server-side.
- **`recipientUserId` is the only field ever used to decide "is this mine."** Never a display name — this is the same rule identity.js established, applied here too, and now a real RLS boundary (`recipient_user_id = auth.uid()`), not just an app-level convention. `actorName` is a cosmetic snapshot only, exactly like order events.
- **Content is role-appropriate at generation time, not display time** — e.g. the `delivery_available` notification (driver pool) is generated with no price anywhere in its message string, because the string itself is what's stored; hiding a price later in some UI wouldn't un-leak a value already sitting in the record.
- **Preferences filter at creation time.** If a category (or one of the three delivery sub-switches — see below) is off for a recipient, the notification is simply never written for them. Turning the preference back on later does not retroactively create what was missed.
- **Mixed defaults within "Delivery updates" are why three types have their own sub-switch** (`deliveryAvailableEnabled`/`deliveryClaimedEnabled`/`deliveryCollectedEnabled`, all default `false`) separate from the category's own default (`true`) — `delivery_cancelled` and `order_delivered` just follow the category, the other three need their own flag because their sensible default disagrees with it.
- `buyer_access_granted`/`buyer_access_revoked` — and, since `0022`, `membership_approved`/`membership_declined` — are **non-configurable** — they always fire regardless of preferences, since they directly affect the recipient's own access (to a role, or to the company itself). The two membership types are registered as non-configurable in `notification_type_enabled_for` for honesty, but — like `site_member_added` — the RPC inserts them unconditionally and never calls that function. Their `navigationTarget` is `{ communityId, role: 'worker' }`; `navigateToNotification`'s existing `eligibleRoles` re-check at click time means a since-declined or since-removed recipient just falls back to `routeFromTop()`.
- **Site notifications (Phase 4B)** — `site_member_added`, `site_member_removed`, `site_archived` — follow the exact same non-configurable pattern for the exact same reason (they change what the recipient can create orders for or purchase), fired from `sites.js`'s `addSiteMember`/`removeSiteMember`/`archiveSite` after their existing `isOwner` gate already succeeded, mirroring how `community.js` fires the buyer-access ones. `removeSiteMember` only notifies if the user was actually a member (checked via `isSiteMember` before the write) — a no-op "remove" call never tells someone they lost access they never had. `site_archived` notifies only the site's **current members** (`getSiteMembers`), not the whole company and not the owner performing it — no other owner-performed CRUD action in this app notifies other owners either. There is deliberately **no** `site_restored` notification, for the same "not every event needs a push" reasoning Phase 3A already applied to `purchase_started`/`purchase_abandoned`/`purchased`/`delivery_returned_to_pool`. Every existing order-lifecycle notification also now carries `siteId` (payload + `navigationTarget`) and names the site in its message text — same types, same recipients, no new types for these, just fuller content.
- **A notification never grants access.** Clicking one (`main.js`'s `navigateToNotification`) always re-checks `eligibleRoles` at click time before routing anywhere — if the stored `navigationTarget` points at a role the user no longer holds, it falls back to `routeFromTop()` instead of opening anything. **Since Phase 4B, it also re-checks `canAccessSite` (`sites.js`) whenever `navigationTarget.siteId` is set** — a stale notification pointing at a site the recipient has since lost access to (removed from the site, or the site's community membership itself is gone) falls back the same way. The one deliberate exception is `role: 'driver'` targets: drivers were never site-scoped in Phase 4A (any approved member can claim any purchased order regardless of site membership), so applying the site check there would incorrectly deny access drivers are supposed to have — `navigateToNotification` skips the site check specifically for driver-routed targets, role/community checks still apply to them as normal. The stored target is a wish, never an authority, for site access exactly as much as it already was for role.
- Opening a notification auto-marks it read; manually toggling back to unread is always available. "Mark all as read" and the unread badge are both scoped to `recipientUserId === currentUserId` — trivially correct since every query is already filtered that way before either ever sees the list.
- The unread badge/panel are **global across all the user's communities**, not scoped to the active one.
- **As of Phase 8D.2, a Realtime subscription exists** (`public/js/realtime.js`'s user-scoped channel, filtered `recipient_user_id=eq.<currentUserId>`) alongside the pre-existing refetch-on-write/view-entry/window-focus pattern every other module uses — `refreshNotificationCache()` is wired into `main.js`'s `refreshDataCaches()` (view entry/focus), into `subscribeAuth` (login/logout/account switch), and now also into that Realtime channel's event handler. **Verified against local Supabase, hosted Supabase, and a genuine second physical device (PC + phone)**: two independent browser sessions of the same account confirmed a notification created in one updates the other automatically, with zero refresh/focus/navigation — a real improvement over the Phase 8D.1-era "only after next refresh" behavior this bullet used to describe. See `supabase/README.md`'s Phase 8D.2 section for the full record of what was tested in each environment.
- **Pruned, not unbounded — this section used to say otherwise, corrected 2026-09-16.** Migration `0029` (`prune_notifications()`, a daily `pg_cron` job) deletes notifications that are both read and older than 90 days; unread ones are never touched regardless of age. Confirmed genuinely scheduled and active on hosted `sitestock-london` (`cron.job`, job name `prune-read-notifications`, `17 3 * * *`), not just present in the migration file. ### Free / Premium plans (migration `0052`, 2026-09-15 — GATING-ONLY, no real billing — pushed, deployed, and hosted-applied to `sitestock-london`)

Founder decision (2026-09-15): every company starts on the **Free plan**, capped at **2 sites**. **Premium** removes the cap for **£10/month**. Signup mentions this once (`index.html`'s register form, a plain hint line — "Every company starts on the Free plan, which includes 2 sites…"); the actual gate is on *creating/restoring a third site*, not at signup, and not a plan-choice step. Verified three ways: the full pgTAP suite (`supabase/tests/40_site_plan_limits.sql`, 41 files / 656 tests, PASS — see PROGRESS.md for a real pre-existing-test regression this caught and fixed along the way), a live walkthrough against the local Supabase stack, and then again **live against real hosted production** after `0052` was applied there (`supabase db push --linked`, run from this session — a disposable test company on `sitestock-london` hit the exact same refusals: a 3rd site blocked with `22023`, a self-flip of `premium` blocked with `42501` — cleaned up afterward via `supabase db query --linked`, which reaches hosted through the Management API with no Docker/direct-Postgres-connection needed at all, worth remembering for future hosted verification work). **The cap is now genuinely enforced in production, not just locally** — this is no longer a "local-only, not yet hosted" caveat.

**This is deliberately gating-only — there is no real payment collection.** Actually charging money needs a registered business and a payment processor (Stripe), whose contracting party must be 18+ — the founder isn't yet (see the `sitestock-launch-blockers` memory). So this build does exactly two things and nothing more: (1) enforce the 2-site cap server-side, (2) let `communities.premium` be flipped manually, by the founder, from the Supabase dashboard/SQL editor, once a real arrangement exists outside the app. There is no Stripe integration, no checkout flow, no self-serve upgrade button, no RPC to request/grant Premium — the Sites screen's upgrade notice is a plain `mailto:` link ("Get notified when Premium is ready"), phrased so it never implies a purchase is currently possible.

- **`communities.premium boolean not null default false`** (migration `0052`). **Not owner-writable, on purpose** — a `BEFORE UPDATE` trigger (`_guard_communities_premium`) refuses any change to this one column when `current_user = 'authenticated'` (the real Postgres role PostgREST switches to for a signed-in app request — see the `statement_timeout` note below on why this, not a JWT claim string, is the reliable signal). Direct SQL (the dashboard, `psql`) and a future service-role webhook both pass straight through untouched, since neither ever runs as `authenticated`. `communities` otherwise has real owner-writable columns on the same row (`require_owner_approval`, `discoverable`, `approval_threshold`, all via the pre-existing `communities_update_owner_only` RLS policy) — this trigger is what stops an owner using dev tools to `PATCH` their own `premium` to `true` for free, which a bare RLS policy on the whole table couldn't distinguish.
- **The cap itself**: `_enforce_site_plan_limit`, a `BEFORE INSERT OR UPDATE` trigger on `sites`. A site counts toward the cap unless it's `archived` — pausing or completing a site doesn't free a slot (it's still in use), only archiving does. Fires on a brand-new site (`INSERT`) and on a site coming back **out of** `archived` (`UPDATE`) — restoring an archived site is the same "now using a slot" event as creating one, and without that second case a Free-plan company could archive+restore to dodge the cap entirely. A plain status change between two non-archived statuses, or any other field edit, never re-triggers the check. `FOR UPDATE` locks the `communities` row while counting, so two concurrent site-creation attempts for the same company can't both slip past a stale count (same discipline as `_enforce_site_budget`, `0033`). Refused with errcode `22023`, message *"Free plan is limited to 2 sites. Upgrade to Premium (£10/month) for unlimited sites."* — surfaced verbatim by `sites.js`'s existing `createSite`/`changeSiteStatus`/`restoreSite` error-return path with zero extra client code needed (defense in depth: the client-side check below is what a user actually sees first).
- **Client-side mirror, display-only**: `sites.js` exports `FREE_SITE_LIMIT` (`2`), `sitesUsedTowardLimit(communityId)` (non-archived site count, mirrors the trigger's own counting rule exactly), and `canCreateMoreSites(communityId)` (`isPremium || used < FREE_SITE_LIMIT`); `community.js` exports `isPremium(communityId)` (reads the cached `premium` flag — read-only, since nothing ever writes it from the client). `sitesView.js`'s `renderPlanStatus()` shows "Free plan · X of 2 sites used" / "Premium plan · unlimited sites" above the create-site form, and swaps the form itself (`#create-site-fields`) for the upgrade notice (`#site-plan-limit-notice`) once `canCreateMoreSites` is false — same "the cache is never the authorization boundary" rule as everywhere else in this app: the DB trigger is what actually stops the write, this is just what shows before the user tries.
- **`terms.html` §10** was updated to disclose the Free plan's 2-site limit and the announced £10/month Premium price, while stating plainly that in-app billing isn't live and nobody is currently charged — matches the actual state, doesn't overclaim.
- **The upgrade notice is a real pop-up modal** (`#premium-upgrade-modal`), not the plain inline card it started as — a navy-to-teal gradient card, bold headline, white pill CTA, and a solid orange circular close button, wired into the same modal/Escape/focus-trap system every other dialog in the app uses (`main.js`'s `DIALOGS` array). Deliberately blue-only (no second accent colour) per explicit direction given while iterating on it. The inline card on the Sites screen (`#site-plan-limit-notice`) is now just a slim "Free plan · X of 2 sites used" reminder with a "See Premium" button that opens the modal — the modal itself carries the actual pitch and the `mailto:` CTA.
- **Not built, deliberately, until an adult can set up billing**: Stripe/any payment processor integration, a checkout or subscription-management screen, a self-serve "Upgrade" button that does anything beyond linking out, webhook handling, proration, invoicing. When that groundwork exists, only the *write path* for `communities.premium` needs to change (whatever the webhook handler sets it from) — the gating logic in this section doesn't need to change at all.

- **Each page's own render function sets its own panel's `hidden`** as `(no content, for the three conditional pages) || currentPage !== 'thatPage'` — there's no separate central "apply visibility" step. If you add a new always-available page, gate its panel the same way (`somePanel.hidden = currentPage !== 'newpage';`) inside its existing render function, right where it already gets called from `render()`.
- **`pageAvailability`** (a plain object, keyed by page name) is set by the three "only show up when there's something to do" pages (`people`/`join-requests`/`buyer-requests`) each render pass — `renderHub()` reads it to decide which names appear in the list at all, exactly preserving the "nothing needing attention hides the whole card, not an empty state" behaviour those three had before they became separate pages. Every other page (`settings`/`analytics`/`activity`/`team`/`orders`) is always listed. If a page you're viewing goes empty out from under you (the last pending request gets decided elsewhere, a Realtime update clears it), `render()` auto-falls-back to the hub — same "stale reference" discipline this app already applies to a since-deleted order or site.
- **`HUB_ITEMS`** is the ordered list `renderHub()` builds the nav from (`{ key, label, conditional?, external? }`). Add a new dashboard section here, give its panel a `.owner-page-back-btn` link + gate its `hidden` by `currentPage`, and it's in — don't hand-write a new nav entry outside this array.
- **One delegated listener** (`document.querySelectorAll('.owner-page-back-btn')`, wired once) handles every page's back-to-dashboard link — never wire a new one individually. This is a **different** button from `orderDetailBackBtn` ("← Back to orders"), which stays scoped to returning from an order's detail view to the Orders page's own list, not to the hub — don't merge these two.
- **A notification's order deep-link still skips the hub entirely** — `refreshOwnerView(orderId)` calls `showOrderDetail(orderId)` directly when the order is found, which sets `currentPage = 'orders'` and opens straight to that order's detail. A plain dashboard entry with no `orderId` now resets to the hub (`currentPage = null`) instead of defaulting into the Orders list the way it used to — that's the actual behaviour change this shipped; the deep-link path was deliberately preserved exactly as before.
- **Don't stack a new dashboard section inline** back onto the always-visible part of `#owner-view` — every new section, however small, should be its own hub page following the pattern above, not a card that always shows regardless of `currentPage`. The Setup checklist is the one deliberate exception (`setupChecklistPanel.hidden = currentPage !== null` — it's hub-only, since it's onboarding guidance pointing *at* the other pages, not a page of its own).

### Owner analytics spend chart (2026-09-15/16, `public/js/owner.js` + `style.css`)

The "This month's spend" hub page gained a **spend-over-time chart** above the existing By-site/By-supplier breakdown, with a period dropdown (`#owner-spend-chart-period`: Daily/Weekly/Monthly/Yearly). It's a **hand-drawn inline SVG**, not a charting library — this app has no build step/npm and the CSP's `script-src` doesn't allowlist a chart CDN, so generating the markup directly in JS was simpler than adding a new external dependency for one chart.

- **Grouped by real purchased spend (`purchasedAt`/`totalPrice`), not the "committed" rule the rest of that page uses.** This deliberately mirrors the dashboard's own "Total Spend (Purchased)" stat tile — a trend of *actual money spent* is more meaningful here than one that includes orders still just pending approval/purchase. `buildChartBuckets(period)` builds the N trailing empty buckets (each carrying its own `match(date)` predicate — day/Monday-start-week/month/year), `buildSpendSeries` sums real orders into them.
- **Every bucket always shows its label and value, including zero-spend ones** — never thinned out or skipped, per explicit direction ("show all the dates and the days"). What keeps this legible at 30 daily points is per-period horizontal spacing (`CHART_PERIODS[period].pxPerPoint`) plus the existing `.spend-chart-wrap` horizontal-scroll container, not hiding labels.
- **The chart auto-scrolls to the most recent period on render** (`monthlyChartEl.scrollLeft = monthlyChartEl.scrollWidth`) whenever it's wider than its container — a real bug found live during this phase's own verification: without it, a returning Owner saw the *oldest* period first and had to scroll right to reach "now," backwards from what anyone actually wants to see by default.
- **First/last point value labels use edge-aware `text-anchor`** (`start`/`end` instead of `middle`) — another real bug found the same way: a centred label on the first or last point clips off the edge of the SVG viewBox.
- **No RPC backdates `purchased_at`** — it's always stamped `now()` server-side inside `complete_purchase`, so there's no legitimate way to produce historical spend data through the app itself. Verifying this chart against a real multi-month/year trend requires seeding disposable orders directly via SQL (local or hosted, always cleaned up afterward) — don't mistake that for a real, reachable app feature; there is still no way for a real Owner to backdate an order's purchase timestamp, on purpose.
- **Deliberately not built**: any chart type beyond a single trend line, per-site/per-supplier breakdowns *within* the chart itself (the existing By-site/By-supplier lists below it already cover that, on the "committed" rule), CSV/image export.

The last four types (Phase 7B) render via the existing generic fallback until a future UI phase gives them their own icon/text in `owner.js`'s `EVENT_RENDER`.

### Phase B — supplier data foundation (suppliers/supplier_branches)

**Status: done.** Moved the branch half of the mock catalog (name, website, postcode, lat/lon — everything `data.js`'s old `BRANCHES` array held) into two real Postgres tables, `suppliers`/`supplier_branches` (`supabase/migrations/0017_supplier_branch_foundation.sql`), as **global SiteStock reference data** — not scoped to any community, since real builders' merchants are the same physical businesses regardless of which community is ordering. `PRODUCTS`/variants/price/availability all **stayed in `data.js`, unchanged** — this was deliberately narrow, the smallest slice a prior architecture review recommended building first; see that review's own output for the full reasoning on why price/stock/product tables were explicitly *not* built this phase.

- **THIS IS MIGRATED FIXTURE/DEMO DATA, NOT MERCHANT-VERIFIED DATA.** Every row in `suppliers`/`supplier_branches` is the exact same demo data that used to be hardcoded in `data.js` — moving it into Supabase for structural reasons does not make it live, official, current, or merchant-sourced. No merchant API/affiliate feed/EDI integration was contacted. Say this explicitly whenever this data comes up — don't let "it's in a real database now" get misread as "it's real merchant data now."
- **Catalogue-key compatibility, the load-bearing design decision**: `supplier_branches.catalogue_key` holds the exact same stable strings (`'b1'`..`'b12'`) `PRODUCTS[].branchIds` and every order's `stockist_id` column already used before this phase existed. `suppliers.js`'s `getBranch`/`getBranchesForProduct` expose branch objects whose `id` is this catalogue key, **never** the new internal `supplier_branches.id` UUID — so every historical order (whose `stockist_id` was always this string format) keeps resolving correctly with zero order-schema change, and `data.js`'s `PRODUCTS[].branchIds` needed zero rewriting.
- **RLS**: `authenticated` gets read-only access to `active = true` rows only, enforced at the RLS layer (not a client-side filter — an inactive row is invisible to a normal `SELECT` regardless of the query sent). **No `INSERT`/`UPDATE`/`DELETE` grant to `authenticated` at all**, for any role including a community Owner — this is global data, no community-level permission concept applies to it, and there is no write RPC. The migration's own seed is the only writer that has ever touched these tables.
- **No Realtime** — `suppliers`/`supplier_branches` are deliberately excluded from the `supabase_realtime` publication (migration `0016` is untouched). This data changes at "someone edits a fixture," not "multiple users collaborate on it live"; the existing bootstrap/view-entry/window-focus refresh (wired into `main.js`'s `refreshDataCaches()` alongside every other cache) is enough.
- **Verified**: local pgTAP (`supabase/tests/09_supplier_branch_foundation.sql`, 21 new tests — table existence, exact seeded counts, unique/FK/check-constraint enforcement, authenticated active-only reads, anon denial, authenticated write denial for both tables, inactive-row exclusion; **full suite 165/165**), full local frontend regression (Worker ranking/order creation, Owner visibility, Buyer snapshot rendering, **Driver pickup-coordinate resolution — the one real regression-risk call site, `driver.js`'s synchronous `getBranch(order.stockistId)`, confirmed correct with zero `NaN`**, edit-order supplier picker, Phase 8D.2 Realtime site-removal fix re-confirmed intact), and the identical matrix re-run against hosted `sitestock-dev` (migration `0017` applied, RLS/grant behavior confirmed via raw REST, a real order placed and resolved correctly end-to-end including Driver pickup distance).
- **Deliberately not built this phase**: `PRODUCTS`/variant tables, any price/stock/offer table, any merchant/affiliate/EDI integration, Edge Functions, merchant-direct delivery, road-distance ranking. `data.js` still owns the entire product side of the catalog.

**Phase B hardening (migration `0018_supplier_parent_activity.sql`)** — a pre-commit audit of Phase B found two real, narrow gaps, both now closed:
- **Parent-supplier inactivity wasn't inherited by its branches.** `0017`'s `supplier_branches_select_active` policy only ever checked the branch's own `active` flag — deactivating a supplier had zero effect on whether its branches were still offered for new orders. `0018` (forward-only — `0017` is already hosted-applied and was never edited) replaces exactly that one policy so a branch is now visible to an authenticated read only if **both** it and its parent supplier are active. No table redesign, no seed/catalogue-key change, no new grant. Verified with a new pgTAP file (`supabase/tests/10_supplier_activity_hardening.sql`, 13 tests covering all four active/inactive combinations plus reactivation) and a corrected expectation in the pre-existing `09_supplier_branch_foundation.sql` (its own fixture setup deactivates "Selco," so the true active-branch count under the fixed policy is 9, not the pre-fix 11) — **full suite now 178/178**.
- **`driver.js` could show a broken "Infinity km from you"/`NaN`-ish distance** when a branch failed to resolve — `distanceKm(pos, null)` returns `Infinity`, and `Infinity != null` is `true` in JS, so the old `dist != null` guard didn't reject it. Fixed with a `safeDistanceKm` helper using explicit `Number.isFinite` checks on all four coordinate values, plus an order-snapshot fallback (`order.stockistName`/`stockistWebsite`/`stockistPostcode`) when the live branch can't be resolved at all (e.g. its supplier went inactive after the order's `stockistId` was snapshotted) — pickup distance is simply omitted in that case, never invented. Driver zero-price display is unaffected (re-confirmed live, no price anywhere in the Driver view).
- **Historical/in-flight order display is unaffected either way** — `stockist_name`/`stockist_website`/`stockist_postcode` on the `orders` table are point-in-time snapshots, never a live join, so a supplier/branch going inactive later never changes how a past order reads. The only live consequence is `driver.js`'s pickup-coordinate lookup, handled by the fallback above.
- **Verified on hosted `sitestock-dev` too**: migration `0018` applied via the normal `supabase db push --linked` workflow (confirmed via `migration list` parity before/after), then the parent-inactivity RLS behavior re-proven directly against hosted via a genuine `SET ROLE authenticated` session (deactivating "Wickes Trade"/"Buildbase" correctly hid exactly their branches from an authenticated read, restored after), plus confirmation that the order referencing a since-hidden branch still carries its own independent snapshot fields. Fixture state fully restored on hosted afterward (all 6 suppliers, all 12 branches active).

## Conventions

- **No comments unless the *why* is non-obvious.** This codebase mostly follows that; keep doing so.
- **Avatars/initials**: always via `getInitials(name)` from `data.js` — single shared implementation, don't reinvent per-file.
- **Relative time**: `timeAgo(ts)` lives in `data.js` alongside `formatPrice`/`getInitials` — import it from there, don't redefine it locally (it used to be duplicated in `communityView.js` and `owner.js`; that's been consolidated).
- **Prices**: always `formatPrice()` from `data.js` (`£X.XX`), never hand-rolled.
- **CSS**: one file, `public/css/style.css`, organized roughly in the order features were built rather than by component — search before adding a new rule, there's likely a close existing pattern (stat tiles, pill buttons, card lists, modal overlay, role-toggle groups, etc.) to extend rather than duplicate. Design-language-wide changes (palette, shape, type scale — not a one-off feature's own styling) belong in the "EDITORIAL REDESIGN LAYER" override block at the end of the file, not scattered into the feature-ordered rules above it — that's the whole reason that block exists (see its own header comment).
- **The app's own UI now matches `landing.css`'s design language exactly, not just its accent colours (2026-09-14).** The accent tokens (`--navy`/`--orange`/`--orange-dark`/`--brown`/`--brown-dark`/`--sand`) already matched `landing.css`'s equivalents byte-for-byte from an earlier pass — this change closed the remaining gap: `:root`'s neutral tokens (`--bg`/`--card`/`--border`/`--text`/`--text-muted`) were repointed to landing's own neutral values (`--landing-paper`/`-white`/`-line`/`-ink`/`-muted` — a cooler, more neutral cream/near-black/faint-border look, replacing the older warmer brown-tinted ones; re-verified against WCAG AA afterward, see the "Contrast" comment block), and the shape language was swept to match landing's actual convention exactly: structural containers (panels/cards/list rows/inputs/modals) stay perfectly square, buttons/pills/toggle-chips/status-badges get landing's soft `4px` corner, and round icon badges (avatar initials, role/product icon tiles, the notif count bubble) became true circles (`50%`) — mirroring landing's `.avatar`/`.role-letter`. **Dark mode was deliberately left untouched** — landing has no dark variant to copy from, so dark mode keeps its own pre-existing warm-dark palette rather than an unreviewed guess; light mode is the one that now matches landing pixel-for-pixel in spirit. Don't introduce a fourth border-radius value without a reason tied back to `landing.css` itself — the point of this pass was to have exactly the same three (0 / 4px / 50%) landing already uses, not to invent a new shape vocabulary.
- **`[hidden]` vs custom CSS display rules**: if you give an element `display: flex/grid/block` in CSS, you **must** also add `.your-class[hidden] { display: none; }` — a plain class rule of equal specificity beats the browser's default `[hidden]` rule and the element stays visible. This has bitten us once already (the session-bar pill leaking onto the login screen); check for it whenever adding `hidden`-toggled elements with non-default `display`.
- **A `<button>` needs an explicit `color`, same as a text input.** The 2026-09-14 dark-mode input fix (`.text-input`/`.search-input` etc. getting `color: var(--text)` alongside `background`) didn't cover buttons — `.result-card` (the hub, Buyer's order list, Sites list, Worker's pickers) went unfixed and rendered near-invisible dark text on a dark `--sink` background in dark mode until 2026-09-16, found live from a founder screenshot. Neither inputs nor buttons inherit `color` from `body` via the UA stylesheet the way ordinary text does — any new button-like element with a themed background needs its own explicit `color` token, checked in both themes, not just assumed from the surrounding text.
- **Testing changes**: verify with the Browser pane tools (`javascript_tool` to drive clicks/form-fills, `get_page_text`/`read_console_messages` to confirm) rather than assuming — this is still the right first move for any in-session change. ### PWA installability (2026-09-14)

The app is installable ("Add to Home Screen"/desktop install prompt) via `public/manifest.webmanifest` + `public/sw.js` + `public/js/swRegister.js`, added as one of the "smaller stuff that doesn't need an adult" launch-checklist items — pure code, no account/payment dependency.

- **`manifest.webmanifest`**: `start_url`/`scope`/`id` are all `"."` deliberately (relative, not `"/"`) — the app is hosted at a GitHub Pages *subpath* (`arcoore.github.io/construction-order-delivery/`), so an absolute root path would be wrong there while still working on local dev, which is exactly the kind of bug that wouldn't show up until a real install was attempted. Three icons: `icon-192.png`/`icon-512.png` (`purpose: "any"`) + `icon-512-maskable.png` (`purpose: "maskable"`, extra internal padding since Android may crop a maskable icon to a circle/squircle) — all three generated from the same navy `#12344a` background + cream "S" glyph as the existing `favicon.svg`, via a one-off Pillow script (not committed — regenerate similarly if the mark ever changes, using `C:/Windows/Fonts/arialbd.ttf` or equivalent bold sans at 72%/62% of the canvas for the standard/maskable variants respectively).
- **iOS needs its own separate mechanism** — Safari's "Add to Home Screen" does not read `manifest.webmanifest` for its icon at all, it uses the pre-existing `<link rel="apple-touch-icon">` (already present, 180×180, untouched) plus the `apple-mobile-web-app-*` meta tags added alongside the manifest link. Both are needed side by side; neither is redundant with the other.
- **`sw.js` is deliberately network-first with zero precaching, not an app-shell/precaching service worker.** This project redeploys straight to `public/` multiple times a day with no build-time versioning or cache-busting for JS/CSS filenames — the perf-pass work earlier explicitly deferred a service worker for exactly this "stale-code risk while redeploying daily" reason (see the memory note this superseded). The fetch handler always tries the network first for every same-origin `GET` and only ever falls back to its runtime cache when the network request itself fails (genuinely offline) — an online user is *never* at risk of seeing stale JS/CSS/HTML through this mechanism, the same guarantee `dev_server.py`'s own `Cache-Control: no-store` protects locally. Cross-origin requests (Supabase REST/Realtime, Turnstile, postcodes.io, Cloudflare Analytics) and non-GET requests are explicitly excluded from interception in the very first line of the fetch handler — the service worker must never sit between the app and a live API call. If you ever need the app to work meaningfully offline (not just "reopen to what you last saw"), that's a deliberately bigger, different feature (a real app-shell precache strategy) — don't casually upgrade this one to do that without reconsidering the staleness tradeoff above.
- **CSP** gained explicit `worker-src 'self'` and `manifest-src 'self'` directives (index.html only — the only page that registers anything) — both would already have worked via the `default-src`/`script-src` fallback chain, but this codebase's CSP is otherwise fully explicit rather than relying on fallback behavior, so these match that convention.
- `public/js/swRegister.js` registers on `window.load` (never competes with critical-path rendering) and is wrapped in a feature check + `.catch(() => {})` — registration failure (e.g. a non-secure-context local setup) must never throw or block the app.
- **Finished 2026-09-14**: the app was installable but undiscoverable — nothing surfaced it beyond the browser's own small, easy-to-miss install icon. `public/js/pwaInstall.js` (new) shows a real "Install SiteStock" banner (same shape as the cookie-consent banner, shown only after that choice is made so the two never stack): a genuine Install button via `beforeinstallprompt` on Chrome/Edge/Android, and manual Share→Add-to-Home-Screen instructions on iOS Safari, which never fires that event at all. Dismissal persists in `localStorage` (`sitestock_pwa_install_dismissed`), same convention as the cookie choice.
