# CLAUDE.md — SiteStock project instructions

Read this before making changes. It's the durable reference: what this project is, how it's built, and the rules that keep it coherent. For "what's done / what's next right now," see [PROGRESS.md](PROGRESS.md) instead — that file changes often, this one shouldn't.

## What this is

A construction-firm ordering & delivery prototype ("SiteStock"). A **Worker** on site searches a materials catalog and requests an order; the community **Owner** approves or rejects it (if the community requires approval — configurable); a **Buyer** (owner-granted only) purchases it externally and confirms with a 3-second hold; an approved **Driver** claims it from the pool, collects it from the chosen stockist, and delivers it. Communities work like Discord servers — an Owner creates one, Workers/Drivers join it (by browsing or invite code, subject to Owner approval) — and everything (orders, requests, roles) is scoped to one community at a time.

This started as a **prototype with no backend**, and **orders/order events/cancellation requests/notifications are still exactly that** — every piece of that data lives only in the browser's `localStorage` on one device, with no real network sync between users. **As of Phase 8B, identity/companies/sites are different**: real Supabase-backed accounts, communities, community memberships, owner grants, buyer grants/requests, sites, and site memberships are now shared server-side, enforced by Postgres RLS (see `supabase/README.md`'s Phase 8B section and this file's "Phase 8B — hybrid backend state" below before assuming either "fully local" or "fully backed" about any given piece of data). Don't casually say "SiteStock has no backend" or "SiteStock is fully multi-device" — both are wrong; say which slice you mean.

## Tech stack

- Plain HTML/CSS/JS. No framework, no build step, no bundler, no npm dependencies (no `package.json`, no `node_modules` — Node still isn't installed, see below).
- JS is native ES modules (`<script type="module">`), loaded directly by the browser — no transpilation. The one exception is `public/js/supabaseClient.js`, which imports the Supabase JS SDK straight from `esm.sh` (a plain browser ES module import over the network, the SDK's own documented buildless usage path — not a build-time dependency, not npm).
- State persistence is split since Phase 8B: identity/companies/sites are Supabase-backed (real Postgres, RLS-enforced — see "Phase 8B — hybrid backend state" below); orders/order events/cancellation requests/notifications, plus two UI-only session pointers (active community/role), are still `localStorage`, wrapped in small pub-sub data modules (see Architecture).
- Styling is one hand-written stylesheet, no CSS framework.

### Running it

Node is **not installed** on this machine — do not reach for it. The dev server is Python:

```bash
python "dev_server.py"
```

`dev_server.py` is a tiny custom static file server (stdlib `http.server`, no dependencies) that serves `public/` on port 3000 **with caching disabled** (`Cache-Control: no-store`). This replaced a plain `python -m http.server` after a real bug: the plain version served stale files after edits (browsers cache-validated against `Last-Modified` and got incorrect 304s within the same second as an edit). Always use `dev_server.py`, never the plain module.

`.claude/launch.json` is already wired to run this via the `preview_start` tool with name `"buyer-replacement"`. It has `"autoPort": true`, and `dev_server.py` reads `PORT` from the environment (falling back to 3000) — needed because this project sometimes gets opened in more than one chat session at once, and the second one can't bind port 3000. Don't hardcode port 3000 anywhere else; always let the tool tell you which port it actually started on.

### The Browser-pane screenshot tool

`computer{action:"screenshot"}` only works if the user has the Browser pane actually open/focused on their end (they click an "Open SiteStock..." affordance in their UI). If it times out with "the Browser pane is not displayed," that's not a bug to fix — just ask the user to open the pane and retry. Text-based verification (`get_page_text`, `javascript_tool`, `read_console_messages`) always works regardless and should be the default way to verify changes; reach for screenshots only when the user explicitly wants to *see* something visual.

## Architecture

### Three layers, by file

**Data layer** (no DOM access, pure state + localStorage + pub-sub):
- `public/js/store.js` — low-level order CRUD (`getOrders`, `addOrder`, `updateOrder`, `subscribe`). UI code must never call this directly for a lifecycle action — see `orderLifecycle.js`.
- `public/js/orderLifecycle.js` — the single guarded entry point for every order state change, plus the append-only order-event log. Also fans out notifications for the relevant events (see "Notification system" below). See "Order lifecycle" and "Worker corrections & cancellation" below.
- `public/js/cancellationRequests.js` — the post-purchase cancellation-request collection (own storage key, own pub-sub). Owns only the collection itself; permission checks live in `orderLifecycle.js`. See "Worker corrections & cancellation" below.
- `public/js/community.js` — **Supabase-backed since Phase 8B** (real `communities`/`community_memberships`/`owner_grants`/`buyer_grants`/`buyer_requests` tables, RLS-enforced): communities, membership, join requests, owner grants, buyer grants/requests, the per-community approval-required setting. Also still owns two genuinely local, UI-only pointers — active community id/active role (never retired to Supabase, never security-relevant). Every read function (`isOwner`, `isApprovedMember`, `isBuyer`, `getOwnerIds`, `getBuyerIds`, `approvedMembers`, etc.) stays **synchronous**, backed by an in-memory cache kept fresh by real async Supabase traffic — see "Phase 8B — hybrid backend state" below for why and its cache-lifecycle rules before touching this file. All keyed by user id — see `identity.js`. Buyer-role actions here also fan out notifications (still local — see `notifications.js`).
- `public/js/sites.js` — **Supabase-backed since Phase 8B** (real `sites`/`site_memberships` tables, RLS-enforced): sites (job locations) within a community, site membership (who's assigned to which site), and the site permission composites (`canAccessSite`, `canCreateOrderForSite`, `canPurchaseForSite`) — same synchronous-facade-over-async-cache pattern as `community.js`. See "Site model" and "Phase 8B — hybrid backend state" below. Not to be confused with `site.js` (singular) below, which is the Worker view — a pre-existing name that predates this module; see that section for why they coexist.
- `public/js/notifications.js` — the single storage/read-state owner for in-app notifications and notification preferences. Still `localStorage`-only (Phase 8B did not touch this — the Postgres schema for it exists unwired, see `supabase/README.md`). See "Notification system" below.
- `public/js/auth.js` — **rewritten in Phase 8B**: real Supabase Auth (email + password), no longer a local plaintext-password account list. Owns Supabase session state only (no profile data) — see "Phase 8B — hybrid backend state" below. "Skip for now" / anonymous guest mode was **removed entirely** in Phase 8B; an account is now required.
- `public/js/supabaseClient.js` — **new in Phase 8B**. The only place the Supabase JS client is instantiated. Every other module that needs Supabase imports `supabase` from here.
- `public/js/identity.js` — resolves "who is the current user"; the only source of truth for permission-relevant identity (see "Identity model" below). **Rewritten in Phase 8B**: no more anonymous guest sessions (removed along with "Skip for now") — `getCurrentUserId`/`getCurrentDisplayName` read the live Supabase session directly; `resolveDisplayName(userId)` for *other* users stays synchronous over a `profiles`-table cache (see "Phase 8B — hybrid backend state" below).
- `public/js/data.js` — static mock catalog (products, stockist branches) + pure helpers (`searchProducts`, `formatPrice`, `getInitials`, `getCategoryIcon`, `getAvailability`, `timeAgo`)
- `public/js/geo.js` — UK postcode geocoding via postcodes.io (free, keyless) + haversine distance + browser geolocation

**UI layer** (owns a chunk of DOM, renders from data-layer state, wires its own event listeners):
- `public/js/authView.js` — the login/register screen (real Supabase email+password since Phase 8B; the "Skip for now" option is gone)
- `public/js/communityView.js` — the Communities management screen (create/join-by-code/browse/your-communities/pending-requests)
- `public/js/site.js` — Worker view (**select site** → search → size → details → source → confirm → order history), plus (Phase 7C) editing/cancelling/requesting cancellation of the Worker's own orders — see "Worker corrections & cancellation" below. The filename predates the Phase 4A "Site" domain concept and still refers to the worker's job location in the loose everyday sense (`site-orders-list`, `renderSiteOrders`, etc.) — this was a deliberate decision (see PROGRESS.md Phase 4A) not to rename it, since there's no runtime collision with `sites.js`/`sitesView.js` (different files, different identifiers), only a naming-adjacency a reader should be aware of.
- `public/js/owner.js` — Owner view (dashboard stats, real event-log activity feed, Team/grant panel, join-request approval, buyer-request approval, approval-setting toggle, order approval/status tabs incl. Cancelled, read-only per-order detail/timeline — see "Owner order visibility" and "Worker corrections & cancellation" below)
- `public/js/driver.js` — Driver view (location, Requests/My Deliveries/Completed tabs, claim/collect/deliver/cancel)
- `public/js/buyer.js` — Buyer view (list of orders awaiting purchase with full cost, review detail, press-and-hold-3s Purchased confirmation), plus (Phase 7C) a cancellation-requests panel for approving/rejecting Worker cancellation requests — see "Worker corrections & cancellation" below
- `public/js/sitesView.js` — Sites management screen, owner-only (list active/archived sites, create, site detail with edit/archive/restore, employee assign/remove, per-site order list). See "Site model" below.

Each UI module exports a `refreshXView()` used by `main.js` to force a clean re-render when the user switches context (e.g. re-entering after switching community).

**Orchestrator**:
- `public/js/main.js` — the only module that knows about *all* the views. Owns `showOnly(view)` (toggles `.view.active` across every `<section>`), the topbar (community/profile pills, session bar, account dropdown), and all cross-cutting routing logic (`routeFromTop`, `enterCommunityFlow`, `showAuth/showCommunityPicker/showCommunitiesView/showProfile/showRoleSelect/showRoleView`). If you need to add a new top-level screen, it goes in `main.js`'s `ALL_VIEWS` array and gets a `showX()` function there — don't reinvent view-switching elsewhere.

Pattern to follow: data modules never touch the DOM; UI modules never read/write `localStorage` directly (they call data-module functions); `main.js` never renders content itself, only decides which section is visible and calls the UI modules' `refreshXView()`.

### Pub-sub convention

Every data module exposes `subscribeX(fn)`: adds `fn` to a listener set, **calls `fn()` immediately** on subscribe (so callers don't need a separate initial render), and re-calls every listener on any mutation. Cross-tab sync piggybacks on the native `storage` event (listed explicitly per-key in each module — if you add a new localStorage key to an existing module, add it to that module's `storage` listener too, or cross-tab/other-view updates silently stop working for it).

### View flow (who can reach what)

```
auth-view (login/register)
  → community-view (front page: name + Log in/Show profile + Go to Communities)
      → communities-view (create / join-by-code / browse / your communities / pending requests)
          → role-select-view (fallback only — see below)
              → worker-view | owner-view | driver-view | buyer-view
                  → sites-view (owner-only, reached via the "Sites" topbar pill — see "Site model" below)
      → profile-view (account details + community memberships + buyer-access request + log out)
```

**Role resolution has no per-visit prompt for real accounts.** At signup, an account answers "worker/driver/owner" once (`account.defaultRole`). Entering any community calls `resolveEntryRole(communityId, userId, preferredRole)` (`community.js`):
1. If they're actually the Owner here (creator, or granted — see below) → straight to `owner-view`, no matter what they picked at signup.
2. Else if their `defaultRole` is worker/driver and they're an approved member → straight there.
3. Else (e.g. picked "owner" but isn't this community's owner) → falls back to `worker-view`.

`role-select-view` ("Choose your role") is reached only as a **fallback** now — every real signup requires picking worker/driver/buyer/owner (no more "Skip for now" path that could leave `defaultRole` unset). It's kept for the defensive case of an account somehow missing a `defaultRole`, and for `menuSwitchRoleBtn` (an account without a fixed preference switching roles manually). Don't remove it.

### Identity model

**Rewritten in Phase 8B.** `identity.js` resolves "who is the current user" from the live Supabase Auth session — every other module asks it rather than touching session/profile state directly. There is no anonymous/guest identity anymore ("Skip for now" was removed entirely; an account is required).

- `getCurrentUserId()` — the real Supabase `auth.users.id` (a UUID) of the logged-in account, or `null` if unauthenticated.
- `getCurrentDisplayName()` — the current account's `display_name`, read straight from the session's own `user_metadata` (set once at signup) — no extra fetch needed for your own name.
- `resolveDisplayName(userId)` — looks up *another* user's display name, synchronously, from an in-memory cache backed by the `profiles` table (real Postgres, `select`-readable by any authenticated user via RLS — see `supabase/migrations/0009_rls_policies.sql`). A cache miss kicks off a background fetch and returns `'Unknown'` in the meantime, same graceful-degradation shape the old guest-lookup fallback used; the next render (triggered once the fetch resolves) shows the real name. `community.js`/`sites.js` also proactively bulk-prime this cache on their own cache loads, so the common case (an already-known member) never shows the placeholder at all.

**All permission/ownership checks in `community.js`/`sites.js` are keyed by `userId`, never by display name.** This is unchanged from before Phase 8B and just as important now: display names are cosmetic labels only. Order records (`store.js`) keep both: an `*Id` field for logic (`requestedById`, `driverId`, `approvedById`, `rejectedById`) and a parallel display-name string snapshot (`requestedBy`, `driver`, `approvedBy`, `rejectedBy`) taken at the time of the action, so historical order cards still read correctly even if a display name changes later.

### Owner permission model

- `isCreator(communityId, userId)` — true only for whoever's id matches `community.ownerId` (`communities.owner_id` in Supabase — set once at creation, never changes).
- `hasOwnerGrant(communityId, userId)` — true if the creator has explicitly granted this user owner access. **Supabase-backed since Phase 8B** (`owner_grants` table, RLS: only the true creator may insert/delete a row — see `supabase/migrations/0009_rls_policies.sql`).
- `isOwner(communityId, userId)` = `isCreator(...) || hasOwnerGrant(...)`. This is the function almost everything else should call — `isCreator` is only for gating the "Team" grant/revoke UI itself (only the true creator can grant/revoke; a granted owner cannot grant further). Synchronous, cache-backed — see "Phase 8B — hybrid backend state" below.
- Granting fires a one-time "You've been upgraded to owner level" popup for the *recipient's* browser session, tracked via the still-local `sitestock_seen_grants_v1` (a UI "have I shown this" flag, not real data — deliberately not moved to Supabase) so it never repeats (see `findUnseenGrantFor`/`markGrantSeen` in `community.js`, wired in `main.js`'s `checkForNewOwnerGrant`).

### Buyer permission model

Unlike worker/driver (bundled free with approved membership), **buyer access is owner-granted only** — `isBuyer(communityId, userId)` = `hasBuyerGrant(...)`, mirroring the owner-grant shape exactly (**Supabase-backed since Phase 8B**, `buyer_grants` table). This is deliberate: buyer handles real purchasing/financial responsibility, so it shouldn't be automatic. Two ways in: an approved member requests it (`requestBuyerRole`, surfaced on the Profile screen), and any owner (not just the creator — this one isn't creator-restricted) approves/declines via the Team-adjacent "Buyer access requests" panel in `owner.js`; or an owner grants it directly from the Team panel without a request. `buyerRequestStatus(communityId, userId)` returns `'none' | 'pending' | 'granted'` for the Profile UI.

### Site model (Phase 4A)

A **Site** is an individual job location (e.g. "24 High Street") that belongs to exactly one community — a company can have many. Sites live in `sites.js`, following the exact same module shape as `community.js`: its own pub-sub (`subscribeSites`), and — **since Phase 8B** — its own real Postgres tables instead of its own localStorage keys (see "Phase 8B — hybrid backend state" below for the cache-facade pattern this module now uses).

- **Storage**: `sites` and `site_memberships` tables (real Postgres, RLS-enforced — see `supabase/migrations/0004_sites.sql`/`0009_rls_policies.sql`); many-to-many (a site can have any number of employees, an employee can belong to any number of sites; neither side ever assumes 1:1).
- **Ownership/CRUD**: `createSite`/`updateSite`/`archiveSite`/`restoreSite` are all owner-only (`isOwner(communityId, actorId)`, reused from `community.js` — not reinvented) and, since Phase 8B, genuinely `async` (real Supabase writes, RLS-checked server-side too). No permanent delete — see the archive note below.
- **Membership**: `addSiteMember`/`removeSiteMember` are owner-only, `async` since Phase 8B, and require the target user to already be an approved community member (`isApprovedMember`) — site membership is a *further restriction inside* company membership, never a substitute for it.
- **Permission composites** — the only functions anything outside `sites.js` should use to decide "can this user do X with this site":
  - `canManageSite(communityId, userId)` — owner only.
  - `canAccessSite(siteId, communityId, userId)` — owner, or a member of that specific site.
  - `canCreateOrderForSite(siteId, communityId, userId)` — owner, or an approved community member who's *also* a member of that site.
  - `canPurchaseForSite(siteId, communityId, userId)` — owner, or a buyer who's *also* a member of that site.
  
  **Every one of these independently re-derives the site's real `communityId` and refuses if it doesn't match the `communityId` argument** (`siteBelongsToCommunity`, private) — `isSiteMember(siteId, userId)` alone only proves membership of a siteId, not that the site actually belongs to the community being checked against. This was a real gap caught during Phase 4A verification (a caller passing a mismatched `communityId` could otherwise let membership in one company's site satisfy a permission check scoped to a different company) and fixed at the module boundary rather than trusting every call site to pre-validate the pair — same "reference is not permission" discipline as the rest of this codebase. Always call these composites rather than reassembling the logic ad hoc, and always pass `communityId` explicitly — never infer it from `getActiveCommunityId()` inside a permission check, since a user can belong to multiple communities and the active one is session state, not a security boundary.
- **Drivers get no site permission function at all, on purpose.** A driver's access to site info is entirely mediated through order visibility (already gated by `isApprovedMember`, unrelated to sites) — they only ever see the site name/address/postcode/delivery-instructions *snapshot already sitting on an order they can already see*, never a live site record or the site's employee list.
- **Archiving, not deleting.** `status: 'active' | 'archived'` on the site record. Archiving only removes a site from the pickers used to start *new* orders (`getActiveSitesForUser`) — it never touches, blocks, or cancels any order already in flight; the order lifecycle is completely independent of live site status. No permanent-delete function exists.
- **`getActiveSitesForUser(communityId, userId)` has the same owner bypass as the permission composites (Phase 5).** It's the site-picker listing helper behind the worker order-creation flow (`site.js`'s `renderSiteSelectList`) — before Phase 5 it only ever consulted membership rows, so an owner who hadn't separately added themself as a site member couldn't see their own site in that picker, even though `canCreateOrderForSite` already let them create an order for it. That was a real UI/permission mismatch (not a security gap — the data-layer check already allowed it), fixed by returning every active site in the community when the caller `isOwner`, exactly mirroring `canAccessSite`/`canCreateOrderForSite`/`canPurchaseForSite`. A normal (non-owner) worker still needs a real membership row — the bypass only ever applies to an actual owner.
- **Renaming a site never rewrites history.** Every order snapshots `siteName`/`siteAddress`/`sitePostcode`/`siteDeliveryInstructions` once at creation (see Order shape below) — editing or archiving the live site record afterward never changes how a past order reads.

### Phase 8B — hybrid backend state

Identity, companies (communities), and sites moved to real Supabase (Postgres + Auth + RLS) in Phase 8B. **Orders, order events, cancellation requests, and notifications did not** — they're still exactly the localStorage-only system described elsewhere in this file, untouched. Don't say "SiteStock has no backend" (identity/companies/sites are real now) or "SiteStock is fully multi-device" (a worker's placed orders still only exist in the browser that created them) — say which slice you mean. Full detail, including what was tested, lives in `supabase/README.md`'s "Phase 8B — frontend wiring (hybrid)" section; this is the load-bearing summary for day-to-day work in `public/js/`.

**Why a synchronous facade over an async cache, not a full async rewrite:** `orderLifecycle.js` and the owner/buyer/driver/site UI modules (`owner.js`, `buyer.js`, `driver.js`, `site.js`) call `isOwner`/`isApprovedMember`/`isBuyer`/`canAccessSite`/`canCreateOrderForSite`/`canPurchaseForSite`/`getCurrentUserId`/`getCurrentDisplayName`/`resolveDisplayName`/`getOwnerIds`/`getBuyerIds`/`approvedMembers`/`getSite` **synchronously, inline, inside render/write code** — 33+ call sites across those four UI files alone. Those files were deliberately kept out of Phase 8B's scope (orders stay local; converting them to async would be the much larger, separately-scoped shared-order migration). Since a real Supabase call is asynchronous, `identity.js`/`community.js`/`sites.js` do the real async I/O internally but keep exposing the exact same synchronous function signatures as before, backed by an in-memory cache. **Every one of the functions named above must stay synchronous** — do not `await` them, do not make their call sites in the four excluded files (or in `orderLifecycle.js`) `async`, and do not add real-time correctness expectations that would require them to be. If a genuine full-async conversion is ever wanted, it's a deliberate future decision for the shared-order migration phase, not an incidental change.

**The cache is never the authorization boundary — RLS is** (`supabase/migrations/0009_rls_policies.sql`). A stale cache can at worst show a UI affordance a user is no longer entitled to use; the actual Supabase write is independently re-checked server-side and refused if it should be, regardless of what the client cache said. This was directly verified (see `supabase/README.md`) with real unauthorized-write attempts against the raw Supabase client.

**Cache lifecycle** — read this before adding a new mutating function to `community.js`/`sites.js`/`identity.js`:
- Refresh on login/logout: `community.js`/`sites.js` each `subscribeAuth(() => refresh...Cache())` internally.
- Refresh after every write: mutating functions update the cache from the server's own returned row before resolving — never an optimistic guess.
- Explicit async bootstrap in `main.js` (awaits session restore + an initial full cache load) before the very first `routeFromTop()` — nothing renders a role view off an empty cache. `index.html`'s `#bootstrap-loading` panel covers the screen meanwhile.
- Refetch on view entry: `main.js`'s routing functions (`showRoleView`, `showRoleSelect`, `enterCommunityFlow`, `showCommunitiesView`, `showSitesView`, `showProfile`) each `await` a cache refresh before rendering.
- Refetch on window focus: a lightweight `window.addEventListener('focus', ...)` in `main.js`.
- **No Supabase Realtime yet** (deliberately deferred) — this means `owner.js`/`buyer.js`/`driver.js`/`site.js` specifically (which subscribe to order/cancellation-request changes, not community/site changes) can show briefly stale community/site data between their own render triggers if something changed in another session. Documented, accepted limitation — don't "fix" it by giving those four files new subscriptions without discussing scope first, since that's exactly the kind of incidental expansion the "don't touch these files" boundary above is meant to prevent.

### Order lifecycle

The order state machine and its append-only event log both live in `orderLifecycle.js` — **UI code must never call `store.js`'s `updateOrder` directly for a lifecycle action.** Every transition goes through a guarded function there (`approveOrder`, `rejectOrder`, `revertApproval`, `startPurchase`, `abandonPurchase`, `completePurchase`, `claimDelivery`, `collectDelivery`, `cancelDelivery`, `deliverOrder`), which re-reads the order fresh, checks the transition is legal from its *current* status (and, where relevant, that the actor is actually allowed — e.g. only the assigned driver can collect/cancel/deliver their own claim), applies the patch, and appends one or more events. An invalid call is refused with `{ ok: false, error }` regardless of what the UI happened to render — this is what makes invalid transitions structurally impossible, not just hidden.

```
pending_approval ──approve──▶ pending_purchase ──start_purchase──▶ purchase_in_progress
       │                            ▲  │                                  │
     reject                         │  └──revert (within 72h)─────────────┘
       ▼                            │                              complete_purchase │ abandon_purchase
   rejected ───revert (within 72h)──┘                                     ▼
                                                                       purchased ◀──────────────┐
                                                                           │ claim               │
                                                                           ▼                      │
                                                                       claimed ──cancel (reason)──┘
                                                                           │ collect
                                                                           ▼
                                                                       collected
                                                                           │ deliver
                                                                           ▼
                                                                       delivered
```

- Worker's `site.js` creates an order via `orderLifecycle.createOrder`, which starts it at `pending_approval` or `pending_purchase` depending on the community's `isApprovalRequired()` setting (toggle in `owner.js`, off by default *stays* off for existing orders — each order snapshots `approvalWasRequired` at creation so a later setting change never silently reinterprets it). `createOrder` also independently re-checks `canCreateOrderForSite(siteId, communityId, actorId)` (`sites.js`) before writing anything and refuses with `{ ok: false, error }` if it fails — this is a real data-layer check, not just a UI gate, so a worker can't create an order for a site they aren't assigned to no matter what got rendered. On success it snapshots the site's `name`/`address`/`postcode`/`deliveryInstructions` onto the order (see Order shape below). `startPurchase` has the equivalent check via `canPurchaseForSite`.
- Owner approves/rejects (`pending_approval` only). A decision can be **reverted** within a 72-hour window (`REVERT_WINDOW_MS`, exported from `orderLifecycle.js`) — but only if `approvalWasRequired` is true, and only while the order is still `pending_purchase`/`rejected`. The lock point is `purchased`, not `picked_up`/`collected` as in the old model — once a buyer has actually spent money, reverting the *approval* doesn't undo that, so it stops being offered.
- Buyer reviews (full cost visible), then must **press and hold "Purchased" for 3 real seconds** (`buyer.js`, `pointerdown`/`pointerup` driving `startPurchase`/`completePurchase`/`abandonPurchase`) — the hold is a confirmation that they already paid externally, not SiteStock processing anything. The hold itself is a real state (`purchase_in_progress`), which is what stops two buyers from both confirming the same order at once, exactly like driver claiming below.
- Driver claims (`purchased → claimed`, first fresh-read wins — this is also how the driver double-claim race is closed, safely within one browser: the guard always re-reads localStorage before writing, so a stale in-memory order object can never win a write), collects, then delivers. Delivering requires the driver to fill in **when** it was delivered (`deliveryTime`, a datetime-local input) and **where** (`deliveryLocation`, free text, pre-filled with the original delivery postcode but editable) before `orderLifecycle.js`'s `deliverOrder` will accept it — both are required at the data layer, not just the form. `deliveredAt` is recorded automatically alongside them (system timestamp of confirmation) and is deliberately kept distinct from the driver-reported `deliveryTime`, since they can differ (e.g. confirmed later due to no signal). No photo proof — deliberately out of scope. **Drivers never see `unitPrice`/`totalPrice`** — stripped from `driver.js`'s render entirely, not just unused.
- Driver can **cancel** a claimed (not yet collected) delivery — reason required, order returns to `purchased` (back in the pool), `driver`/`driverId` cleared on the order but preserved in the `delivery_cancelled` event's `meta` (since the order's own fields no longer have it) alongside `purchasedById`, which is exactly what the `delivery_cancelled` notification (see below) uses to tell the buyer who dropped it and why.

### Worker corrections & cancellation (Phase 7B data layer, Phase 7C UI)

A genuine new terminal status, **`cancelled`**, was added to `TRANSITIONS` (distinct from `rejected` — rejected means the Owner said no before purchase, cancelled means the Worker withdrew it, sometimes after money was spent; conflating them would blur exactly the accountability distinction this codebase already goes out of its way to preserve elsewhere). It's reached from three different places, all through one shared action key so the state machine doesn't fork into two "cancelled" flavors:

```
pending_approval ──cancel_order──▶ cancelled ◀──cancel_order── pending_purchase
                                        ▲
                     purchased/claimed ─┘  (cancel_order, Buyer-approved only)
```

- **`editOrder(orderId, fields, actorId, actorName)`** — a Worker correcting their own order (`requestedById === actorId`, re-checked fresh, no Owner override in this phase). Which action key it hands to the shared `applyTransition` engine depends on more than status alone, since `pending_purchase` is reached two different ways:
  - `pending_approval`, or `pending_purchase` with `approvedById` still `null` (approval was off for this order) → action `edit`, a same-status transition (nothing's been signed off, nothing to protect).
  - `pending_purchase` with `approvedById` set (a real Owner approval happened) → action `edit_and_reapprove`, which resets status to `pending_approval` **and clears the approval fields in the same patch** — editing an already-approved order can never silently survive as the version the Owner actually signed off on. This reuses the exact `pending_purchase → pending_approval` edge the Owner's own manual revert already used, just Worker-triggered, rather than a second parallel change-request system.
  - `purchase_in_progress` and everything `purchased`-and-beyond: refused outright, before `applyTransition` is ever called.
  - Only a fixed field whitelist (`EDITABLE_ORDER_FIELDS` in `orderLifecycle.js`) is ever accepted from the caller — `requestedBy`/`requestedById`/`createdAt` and every actor/status field are never in it, so a caller can't smuggle a provenance or status change in through the patch. A `siteId` change is authorized exactly like `createOrder` does (`canCreateOrderForSite`, active-site check, community match) and re-snapshots `siteName`/`siteAddress`/`sitePostcode`/`siteDeliveryInstructions` from the *new* site's live record — never trusting caller-supplied site text.
  - Logs **two** events from the one transition when it forces reapproval — `order_edited` (carrying `meta.changes`, a `{ field: { from, to } }` diff of only what actually changed) and `approval_reverted` (the exact existing type, reused) — the same multi-event-per-transition shape `cancelDelivery` already uses (`delivery_cancelled` + `delivery_returned_to_pool`). The original `approved` event from when the Owner first signed off is never touched — events are append-only; this only adds to the record. An edit reusing `order_awaiting_approval` (unchanged type) re-notifies the Owner, since a Worker's edit is genuinely new work for them — unlike the Owner's own revert, which doesn't re-notify since they obviously already know.
- **`cancelOrderDirect(orderId, actorId, actorName, reason)`** — instant, Worker-initiated, only legal at `pending_approval`/`pending_purchase` (regardless of how `pending_purchase` was reached — the boundary here is *money spent*, not approval, unlike editing). Refuses with a specific, retryable message at `purchase_in_progress` (the Buyer's hold resolves in seconds either way) rather than a generic transition error.
- **Post-purchase, cancellation becomes a request, not a direct action** (`purchased`/`claimed` only — blocked from `collected` onward, since the goods are then physically with the driver and approving a cancellation would need a way to tell them to stop, which this phase deliberately doesn't build). `requestCancellation`/`decideCancellationRequest` in `orderLifecycle.js` coordinate a brand-new collection, `cancellationRequests.js` (`sitestock_cancellation_requests_v1`), following the exact module shape `community.js` already established twice for join/buyer requests — its own storage key, its own pub-sub, its own `pending`/`approved`/`rejected` row per request, only one pending request per order at a time. The request module owns nothing but the collection itself; every permission check (is this actor the order's requester, is this actor a currently-valid buyer for the site via `canPurchaseForSite`) lives in `orderLifecycle.js`, layered on top — the same separation already used between `sites.js`'s own CRUD checks and `orderLifecycle.js`'s own `createOrder` authorization.
  - **`order.status` is left completely untouched while a request is pending** — a Driver can still claim/collect normally; nothing about claiming is gated on whether a request exists. When the Buyer decides, `decideCancellationRequest` re-reads both the request and the order fresh and re-attempts the underlying `cancel_order` transition — which has **no edge at `collected`**, so an order a Driver has since collected refuses *at the table itself*, not via a hand-written status check. On that refusal the request is deterministically auto-closed as `rejected` (with a system-generated `decisionReason`) rather than left dangling as `pending` forever, and a `cancellation_rejected` event is logged — the Worker gets a truthful outcome instead of silence.
  - Approval clears `driver`/`driverId`/`claimedAt` on the order (mirroring how a Driver's own `cancelDelivery` already clears them) while preserving the departing driver's identity in the `order_cancelled` event's `meta` (`previousDriverId`/`previousDriverName`) — and, since the Driver otherwise has no way to learn the thing they claimed is no longer needed, they're added as a recipient of the same `cancellation_approved` notification the Worker gets, not a new notification type.
  - **Only four new event types exist**: `order_edited`, `order_cancelled`, `cancellation_requested`, `cancellation_rejected`. There is deliberately no separate `cancellation_approved` *event* — an approved request's order-level consequence is already fully captured by `order_cancelled` with `meta.via: 'cancellation_request'` (vs. `'direct'`), so a second event for the same instant would be redundant. `cancellation_approved` only exists as a *notification* type.
  - `orderCancelledBy`/`orderCancelledById`/`orderCancelledAt`/`orderCancellationReason` (new, additive order fields, set by either cancellation path) are **deliberately distinct** from the pre-existing `cancelledBy`/`cancelledById`/`cancelledAt`/`cancellationReason`, which mean something different (a Driver dropping their own delivery claim — order stays alive) — reusing those names for the order's own terminal cancellation would quietly conflate two unrelated events.
  - **No `sitestock_orders_v4` version bump** — every new field is additive/nullable, and `cancelled` is just a new value for the existing `status` field, matching the precedent already set for `requireOwnerApproval` and `siteId`. `sitestock_cancellation_requests_v1` is a brand-new collection, same as `sitestock_sites_v1` was in Phase 4A.
- **Worker UI (`site.js`, Phase 7C)**: each of the Worker's own order cards (`order.requestedById === currentUserId`, checked in the UI purely to decide what to *show* — the real gate is always the guarded function itself, re-checked when a button is actually pressed) gets "Edit order"/"Cancel order" in Zone 1/2, or "Request cancellation" once purchased/claimed, or nothing once a request is already pending (shown instead as "Cancellation requested — awaiting Buyer decision", or "Cancellation rejected: <reason>" if their last request was declined — both derived from `cancellationRequests.js`, not the raw event log). Direct cancel reuses `buyer.js`'s exact press-and-hold pattern (`.hold-confirm-btn`, 3000ms) but only calls `cancelOrderDirect` once at the *end* of a completed hold — unlike the Buyer's purchase hold, there's no data-layer "in progress" lock to create/abandon partway through, since a direct cancel is a single atomic action. The edit form is one consolidated panel (`editState.mode`: `summary`/`pick-material`/`pick-variant`/`pick-source`/`pick-site`) rather than the full multi-step creation wizard reused as separate screens — deliberately simplified per explicit direction, while still reusing the exact same underlying data (`searchProducts`/`getBranchesForProduct`/`getAvailability`/`getActiveSitesForUser`) and picker markup (`.result-card`/`.variant-list`/`.source-option`) the creation wizard already uses. Changing the site only ever offers `getActiveSitesForUser`'s own list — never free text — so an unauthorized site can't even be selected in the UI, on top of `editOrder`'s own independent re-check. If the edit would invalidate a real Owner approval, a persistent hint ("Changing this order will require the Owner to approve it again") is shown before the Worker can save, not as a second approval system.
- **Buyer UI (`buyer.js`, Phase 7C)**: a "Cancellation requests" panel (hidden when empty, matching the exact show/hide pattern `owner.js`'s join/buyer-request panels already use) lists every `pending` request whose order the current Buyer can act on via `canPurchaseForSite` — the same check `decideCancellationRequest` itself re-runs, so this list is a display convenience only, not an independent permission surface. Approve/Reject both reveal an inline deliberate-confirmation step (reusing the `.reject-form` pattern already used three times elsewhere) rather than a press-and-hold — a cancellation decision is reversible in spirit (nothing's committed until confirmed) the way the Buyer's own purchase-hold isn't, so the lighter pattern is the correct fit, not an inconsistency. A refusal returned by the data layer (e.g. the order was collected before the decision landed) is shown verbatim, never silently treated as success.
- **Owner UI (`owner.js`, Phase 7C)**: a seventh tab, **Cancelled** (`TAB_GROUPS.cancelled = ['cancelled']`), kept deliberately separate from Rejected. `EVENT_RENDER` gained entries for all four Phase 7B event types, including a structured, human-readable diff for `order_edited` (e.g. "quantity 10 → 15, site Site A1 → Site A2" — raw id/sub-fields like `siteId`/`sitePostcode` are filtered out of the summary, though they're still present in the underlying `meta.changes` for anyone reading the raw event) and a rendering fork for `cancellation_rejected` that distinguishes a real Buyer decision from the automatic close-out when a Driver collects an order before anyone decides (`meta.autoClosed`) — the timeline never attributes the auto-close to "the buyer," since no buyer actually acted. `renderOrderCard`'s revert-section branch was given an explicit `cancelled` case (empty, not the generic `renderRevertSection` fallback) specifically because that fallback's "once purchased, orders can't be reverted" message reads as if a purchase happened even when a `cancelled` order never got that far.
- **Notification click-through** needed no `main.js` changes at all — the generic Phase 6 routing already handles any new type/role/orderId combination. The one addition is in `buyer.js` itself: since a `cancellation_requested` notification points at an order that isn't `pending_purchase` (so `refreshBuyerView`'s existing detail-opening path doesn't apply), a small `highlightCancellationRequestForOrder` scrolls/flashes the right row in the new panel instead — the exact same `.order-card-highlight` class and 2000ms timeout `main.js`'s own `highlightOrderIfPending` already uses, just retargeted at this panel.

### Owner order visibility (Phase 5)

`owner.js`'s order list is grouped into six tabs, all pure UI regrouping of the existing `order.status` values (`TAB_GROUPS` in `owner.js`) — **no new statuses, no new transitions, nothing added to `orderLifecycle.js`'s `TRANSITIONS` table**:

- `awaiting` → `pending_approval`
- `purchase` ("Waiting for Purchase") → `pending_purchase`, `purchase_in_progress`
- `purchased` → `purchased`
- `delivery` ("Out for Delivery") → `claimed`, `collected`
- `delivered` → `delivered`
- `rejected` → `rejected`

This replaced the old three-tab layout (`Awaiting Approval` / `Approved` / `Rejected`) whose "Approved" tab dumped every non-pending, non-rejected order into one undifferentiated pile. The revert-countdown ticking `setInterval` only re-renders on `purchase`/`rejected` tabs now, since `pending_purchase`/`rejected` are the only statuses `orderLifecycle.js`'s revert transition actually applies to (unchanged logic, just retargeted at the new tab names).

Each order card also has a **"View details"** link (`data-detail-id`) opening a read-only per-order detail/timeline view (`owner-order-detail-panel` in `index.html`, `renderOrderDetail` in `owner.js`) — swapped in place of the tabbed list (`owner-orders-panel`), not a separate route. It shows the order fields already on the order (product, site snapshot, sourcing, delivery info when delivered) plus every actor already stored on the order (`requestedBy`/`approvedBy`/`rejectedBy`/`purchasedBy`/`driver`/`cancelledBy`), and a full timeline built from `getOrderEvents(orderId)` reusing the exact same `EVENT_RENDER` icon/text map the dashboard's activity feed already used — **no second history system, no new event schema, nothing fabricated that isn't already sitting on the order or in the event log.** It has no action buttons of any kind (not even revert) — strictly read-only, by design. Selecting an order is `owner.js`-local state (`selectedOrderId`); switching community or losing the order from the live order list (e.g. a stale reference) falls back to the list view automatically via the same `render()` path everything else already goes through.

### Notification system

`notifications.js` owns `sitestock_notifications_v1` (the notifications themselves) and `sitestock_notification_prefs_v1` (per-user preferences) — UI code must never touch either key directly, only this module's exported functions (`notifyUsers`, `getNotificationsFor`, `getUnreadCount`, `markRead`, `markUnread`, `markAllRead`, `getPreferences`, `savePreferences`, `subscribeNotifications`).

- **`recipientUserId` is the only field ever used to decide "is this mine."** Never a display name — this is the same rule identity.js established, applied here too. `actorName` is a cosmetic snapshot only, exactly like order events.
- **Recipients are computed by the callers** (`orderLifecycle.js`, `community.js`), using `community.js`'s own `getOwnerIds`/`getBuyerIds`/`approvedMembers` — `notifications.js` itself stays a leaf with zero permission logic, and the acting user is always excluded from their own notification's recipient list (no self-notifications).
- **Content is role-appropriate at generation time, not display time** — e.g. the `delivery_available` notification (driver pool) is generated with no price anywhere in its message string, because the string itself is what's stored; hiding a price later in some UI wouldn't un-leak a value already sitting in the record.
- **Preferences filter at creation time.** If a category (or one of the three delivery sub-switches — see below) is off for a recipient, the notification is simply never written for them. Turning the preference back on later does not retroactively create what was missed.
- **Mixed defaults within "Delivery updates" are why three types have their own sub-switch** (`deliveryAvailableEnabled`/`deliveryClaimedEnabled`/`deliveryCollectedEnabled`, all default `false`) separate from the category's own default (`true`) — `delivery_cancelled` and `order_delivered` just follow the category, the other three need their own flag because their sensible default disagrees with it.
- `buyer_access_granted`/`buyer_access_revoked` are **non-configurable** — they always fire regardless of preferences, since they directly affect the recipient's own permissions.
- **Site notifications (Phase 4B)** — `site_member_added`, `site_member_removed`, `site_archived` — follow the exact same non-configurable pattern for the exact same reason (they change what the recipient can create orders for or purchase), fired from `sites.js`'s `addSiteMember`/`removeSiteMember`/`archiveSite` after their existing `isOwner` gate already succeeded, mirroring how `community.js` fires the buyer-access ones. `removeSiteMember` only notifies if the user was actually a member (checked via `isSiteMember` before the write) — a no-op "remove" call never tells someone they lost access they never had. `site_archived` notifies only the site's **current members** (`getSiteMembers`), not the whole company and not the owner performing it — no other owner-performed CRUD action in this app notifies other owners either. There is deliberately **no** `site_restored` notification, for the same "not every event needs a push" reasoning Phase 3A already applied to `purchase_started`/`purchase_abandoned`/`purchased`/`delivery_returned_to_pool`. Every existing order-lifecycle notification also now carries `siteId` (payload + `navigationTarget`) and names the site in its message text — same types, same recipients, no new types for these, just fuller content.
- **A notification never grants access.** Clicking one (`main.js`'s `navigateToNotification`) always re-checks `eligibleRoles` at click time before routing anywhere — if the stored `navigationTarget` points at a role the user no longer holds, it falls back to `routeFromTop()` instead of opening anything. **Since Phase 4B, it also re-checks `canAccessSite` (`sites.js`) whenever `navigationTarget.siteId` is set** — a stale notification pointing at a site the recipient has since lost access to (removed from the site, or the site's community membership itself is gone) falls back the same way. The one deliberate exception is `role: 'driver'` targets: drivers were never site-scoped in Phase 4A (any approved member can claim any purchased order regardless of site membership), so applying the site check there would incorrectly deny access drivers are supposed to have — `navigateToNotification` skips the site check specifically for driver-routed targets, role/community checks still apply to them as normal. The stored target is a wish, never an authority, for site access exactly as much as it already was for role.
- Opening a notification auto-marks it read; manually toggling back to unread is always available. "Mark all as read" and the unread badge are both scoped to `recipientUserId === currentUserId` — trivially correct since every query is already filtered that way before either ever sees the list.
- The unread badge/panel are **global across all the user's communities**, not scoped to the active one.
- No polling anywhere — creation happens synchronously in the same call as the state change that caused it; cross-tab sync piggybacks on the native `storage` event, same as every other module here.
- **Known future consideration, not yet solved:** `sitestock_notifications_v1` only ever grows, and `localStorage` has real size limits (~5–10MB). No pruning/capping exists yet — flagged here so it doesn't silently become a problem, not something to fix without being asked.

### Data shapes (informal — no schema/types, just what's actually written)

**Order** (`sitestock_orders_v4`, via `store.js`): `id, communityId, siteId, siteName, siteAddress, sitePostcode, siteDeliveryInstructions, productId, productName, variant, quantity, unit, deliveryPostcode, deliveryLat, deliveryLon, requestedBy, requestedById, status, createdAt, approvalWasRequired, driver, driverId, claimedAt, collectedAt, deliveredAt, deliveryTime, deliveryLocation, stockistId, stockistName, stockistWebsite, stockistPostcode, pickupEstimate, unitPrice, totalPrice, approvedBy, approvedById, approvedAt, rejectedBy, rejectedById, rejectedAt, rejectionReason, purchaseStartedBy, purchaseStartedById, purchaseStartedAt, purchasedBy, purchasedById, purchasedAt, cancelledBy, cancelledById, cancelledAt, cancellationReason, orderCancelledBy, orderCancelledById, orderCancelledAt, orderCancellationReason`. The non-`Id` actor fields are display-name snapshots for rendering only — never used for permission checks; `siteName`/`siteAddress`/`sitePostcode`/`siteDeliveryInstructions` follow the exact same convention (a point-in-time snapshot of the `sites.js` record at creation, alongside the logic-bearing `siteId` — see "Site model" above for why). `deliveryTime`/`deliveryLocation` are driver-reported (Phase 2B); `deliveredAt` is the automatic system timestamp of confirmation — kept distinct on purpose. The last four fields (Phase 7B, additive) are deliberately distinct from `cancelledBy`/`cancelledById`/`cancelledAt`/`cancellationReason`, which mean something different (a Driver dropping their own delivery claim) — see "Worker corrections & cancellation" above. Only ever written via `orderLifecycle.js`, never directly.

**Order event** (`sitestock_order_events_v1`, via `orderLifecycle.js`, append-only — no update/delete is exported): `id, orderId, communityId, type, actorId, actorName, fromStatus, toStatus, reason, meta, createdAt`. Event types: `order_created, approved, rejected, approval_reverted, purchase_started, purchase_abandoned, purchased, delivery_claimed, delivery_cancelled, delivery_returned_to_pool, collected, delivered, order_edited, order_cancelled, cancellation_requested, cancellation_rejected`. This is the real audit trail — `owner.js`'s dashboard activity feed queries it directly rather than reconstructing history from order fields, so a revert no longer erases the events that led up to it. The last four types (Phase 7B) render via the existing generic fallback until a future UI phase gives them their own icon/text in `owner.js`'s `EVENT_RENDER`.

**Cancellation request** (`sitestock_cancellation_requests_v1`, via `cancellationRequests.js`): `id, orderId, communityId, siteId, requestedById, requestedBy, reason, status (pending/approved/rejected), createdAt, decidedAt, decidedById, decidedBy, decisionReason`. Same shape convention as join/buyer requests. Only one `pending` row per order at a time. A `rejected` status covers both a real Buyer decision and the deterministic auto-close that happens if a Driver collects the order before anyone decides — `decisionReason` distinguishes the two in that case.

**Since Phase 8B, the six entries below live in real Postgres, not localStorage** — the JS-camelCase field names here are what `community.js`/`sites.js`/`identity.js` map the Supabase rows to in their in-memory cache; the authoritative column-level schema (types, constraints, foreign keys) is the migration files under `supabase/migrations/`, not this section. Cross-reference by table name if you need the exact SQL shape.

**Community** (Supabase `communities` table): `id, name, code (from invite_code, 6-char invite code), ownerId (from owner_id), createdAt, requireOwnerApproval` (boolean, `require_owner_approval` — additive-in-spirit; defaults `true` at the DB level).

**Join request** (Supabase `community_memberships` table — unifies what used to be a separate `join_requests` concept with "approved member" derived from it into one row with a status): `id, communityId, userId, status (pending/approved/declined), requestedAt, decidedAt, decidedById`.

**Owner grant** (Supabase `owner_grants` table): `id, communityId, userId, grantedById, grantedAt`.

**Buyer grant** (Supabase `buyer_grants` table): `id, communityId, userId, grantedById, grantedAt`. Same shape as owner grant.

**Buyer request** (Supabase `buyer_requests` table): `id, communityId, userId, status (pending/approved/declined), requestedAt, decidedAt, decidedById`. Same shape as join request; approving one also creates the corresponding buyer grant.

**Site** (Supabase `sites` table, cached via `sites.js`): `id, communityId, name, address, postcode, deliveryInstructions, status ('active'/'archived'), createdAt, createdById, updatedAt, archivedAt, archivedById`. `id` is a stable generated id, never derived from or dependent on `name` — two sites (same or different communities) can share a name with zero ambiguity. `archivedAt`/`archivedById` are null until archived. **No `createdBy`/`archivedBy` display-name-snapshot fields since Phase 8B** (Postgres only stores the `*_id`; `sitesView.js` resolves the display name live via `resolveDisplayName(site.archivedById)` instead of trusting a stored string — nothing outside `sitesView.js` reads those two fields, so dropping them was safe).

**Site membership** (Supabase `site_memberships` table, cached via `sites.js`): `id, siteId, communityId, userId, addedAt, addedById`. A plain many-to-many join row — a site can have any number of members, a user can belong to any number of sites in any number of communities. `communityId` is denormalized from the site record purely as a defense-in-depth check inside the permission composites (see "Site model" above) — enforced as a real composite foreign key at the database level (`supabase/migrations/0004_sites.sql`), not just a runtime re-check anymore.

**Account**: **Real Supabase Auth since Phase 8B** — no longer a local record this app owns. `auth.users` (managed entirely by Supabase, real bcrypt-hashed passwords, never touched by app code) plus a `profiles` row (`id, display_name, created_at`) auto-created by a database trigger the moment a user signs up. `defaultRole` lives in the *session's own* `user_metadata` (set once at signup via `supabase.auth.signUp`'s `options.data`), not a table column — it's only ever read for the current user's own account, never looked up for anyone else, so it doesn't need to be queryable. See `auth.js`'s header and `supabase/migrations/0002_profiles.sql`.

**Notification** (`sitestock_notifications_v1`, via `notifications.js`): `id, recipientUserId, type, category, title, message, communityId, orderId, requestId, eventId, siteId, actorId, actorName, navigationTarget, createdAt, read, readAt`. Only `read`/`readAt` are ever mutated after creation — everything else is write-once, same as an order event. `siteId` (Phase 4B) is optional, null when not applicable, and exists purely so `navigateToNotification` can re-verify current site access at click time — there is deliberately no companion `siteName` field, since the site's name already lives inside the pre-rendered `message` string (same "content baked at creation time" rule every other notification already follows). Types: `order_awaiting_approval, order_rejected, approval_reverted, order_ready_for_purchase, delivery_available, delivery_claimed, delivery_cancelled, delivery_collected, order_delivered, buyer_access_requested, buyer_access_granted, buyer_access_rejected, buyer_access_revoked, site_member_added, site_member_removed, site_archived`.

**Notification preferences** (`sitestock_notification_prefs_v1`, via `notifications.js`): `userId, orderUpdates, approvalUpdates, deliveryUpdates, roleUpdates, deliveryAvailableEnabled, deliveryClaimedEnabled, deliveryCollectedEnabled, updatedAt`. No record = all four category presets `true`, all three sub-switches `false` (see "Notification system" above for why the sub-switches exist).

*(The `_v2`/`_v3`/`_v4` localStorage key bumps below apply only to the entities still on localStorage — orders, order events, cancellation requests, notifications, notification preferences. The `_v2` bump on communities/join-requests/owner-grants **historically** reflected the switch from name-string identity to `userId`-based identity, back when those were localStorage keys too — Phase 8B moved all of that to real Postgres tables, described above, which have their own migration-file history instead of a version-suffixed key name. The `_v3` bump on orders reflects the Phase 2A lifecycle rework — renamed statuses and new fields. The `_v4` bump on orders reflects Phase 4A — `siteId` and its snapshot fields became permanent, required parts of the order shape rather than an optional add-on, so every order now has a real site behind it with no "legacy/unassigned site" branching needed anywhere. In all cases old data was intentionally discarded, not migrated, per explicit direction each time — there was nothing reliable to migrate from.)*

Mock catalog (`data.js`): 16 products across categories (Timber, Building Materials, PPE, Plumbing, Tools, etc.), each with a `unitPrice`, a list of `variants` (size/type — every product has at least one, so the "pick material → pick size" flow never skips a step), and `branchIds` referencing 12 mock UK builders'-merchant branches (name, website domain, postcode, lat/lon). ## Conventions

- **No comments unless the *why* is non-obvious.** This codebase mostly follows that; keep doing so.
- **Avatars/initials**: always via `getInitials(name)` from `data.js` — single shared implementation, don't reinvent per-file.
- **Relative time**: `timeAgo(ts)` lives in `data.js` alongside `formatPrice`/`getInitials` — import it from there, don't redefine it locally (it used to be duplicated in `communityView.js` and `owner.js`; that's been consolidated).
- **Prices**: always `formatPrice()` from `data.js` (`£X.XX`), never hand-rolled.
- **CSS**: one file, `public/css/style.css`, organized roughly in the order features were built rather than by component — search before adding a new rule, there's likely a close existing pattern (stat tiles, pill buttons, card lists, modal overlay, role-toggle groups, etc.) to extend rather than duplicate.
- **`[hidden]` vs custom CSS display rules**: if you give an element `display: flex/grid/block` in CSS, you **must** also add `.your-class[hidden] { display: none; }` — a plain class rule of equal specificity beats the browser's default `[hidden]` rule and the element stays visible. This has bitten us once already (the session-bar pill leaking onto the login screen); check for it whenever adding `hidden`-toggled elements with non-default `display`.
- **Testing changes**: this app is entirely click-flow-driven with no automated tests. Verify with the Browser pane tools (`javascript_tool` to drive clicks/form-fills, `get_page_text`/`read_console_messages` to confirm) rather than assuming. Screenshots are a nice-to-have on top, not the primary verification method (see note above).

## Security note (be upfront about this, don't paper over it)

**Updated by Phase 8B — read carefully, this used to say something different.** Authentication itself is now real: Supabase Auth handles password hashing/storage server-side (real bcrypt, not app code, not plaintext) — the app never sees or stores a raw password beyond the login form submission. RLS (`supabase/migrations/0009_rls_policies.sql`) is a real, independently-verified security boundary for identity/companies/sites (see `supabase/README.md`'s Phase 8B section for the specific RLS probes that were run).

**What's still true, and still worth being upfront about**: orders, order events, cancellation requests, and notifications remain plain `localStorage` with zero confidentiality/integrity guarantee beyond the browser they're created in — there is no server-side check on any order-lifecycle action yet, only the client-side guards in `orderLifecycle.js`. Don't describe the app as "fully secured" or "production-ready" — say specifically which slice is real (identity/companies/sites) and which isn't (orders/notifications) until Phase 8C+ changes that. The local Supabase stack itself is dev-only (well-known local anon key, no TLS, no real users) — see `supabase/README.md` before treating any of it as production-grade.

## Things NOT to do without asking

- Don't reach for Node/npm — it isn't installed here. (`public/js/supabaseClient.js` imports the Supabase SDK from `esm.sh` as a plain browser ES module — that's not an npm dependency, don't treat it as license to add real npm tooling elsewhere.)
- Don't "fix" the **order/notification** single-browser/no-sync limitation by inventing a fake backend or fake cross-device sync for that slice — it's a known, accepted constraint until Phase 8C+. (Identity/companies/sites are no longer this limitation — see "Phase 8B — hybrid backend state" above. Don't conflate the two.)
- Don't remove `role-select-view` or its fallback logic — see "View flow" above for why it's still load-bearing even without the old "Skip for now" path.
- Don't reintroduce the old plaintext-localStorage-account or anonymous-guest identity systems — Phase 8B removed both on purpose (see `auth.js`/`identity.js` headers).
- Don't create a production/cloud Supabase project, and don't ever ship the `service_role` key to the browser, without the user explicitly asking for that specific step.
- Don't make `community.js`/`sites.js`/`identity.js`'s read functions (`isOwner`, `isApprovedMember`, `canAccessSite`, `getCurrentUserId`, `resolveDisplayName`, etc.) actually async, and don't add `await` at their call sites in `owner.js`/`buyer.js`/`driver.js`/`site.js`/`orderLifecycle.js` — this would silently turn every `if (isOwner(...))`-shaped check into "always true" (a `Promise` is truthy). If a real full-async rewrite is ever wanted, it's a deliberate, scoped decision for the (not-yet-started) shared-order migration phase, not an incidental refactor.
- Don't call `store.js`'s `updateOrder` directly from UI code for a lifecycle action — always go through `orderLifecycle.js`'s guarded functions, or the state-machine/event-log guarantees silently stop holding.
- Don't decide site access by checking `isSiteMember`/role checks separately and combining them ad hoc — always call `sites.js`'s `canAccessSite`/`canCreateOrderForSite`/`canPurchaseForSite` composites, which already handle the owner bypass and the cross-community `communityId` cross-check correctly in one place.
