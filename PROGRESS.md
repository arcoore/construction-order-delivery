### Order lifecycle migration to Supabase (Phase 8C)

- **Implemented and locally verified, following an approved 16-step implementation order and a detailed pre-approved specification — committed as `1f4adf8` ("Move order lifecycle to Supabase") and pushed to `origin/main`.** Moved orders, order events, and cancellation requests from `localStorage` to real Supabase (Postgres + RLS + RPC), closing the last major gap from Phase 8B. **Only in-app notifications/notification preferences remain localStorage-only now.**
- Migration `0012_widen_edit_order.sql`: widened the Phase 8A `edit_order` RPC to the full field set the Worker edit form actually needs, added a non-negative `unit_price` CHECK constraint, and made `total_price` always server-computed (`unit_price × quantity`) — the browser can never set it directly. Added 9 new pgTAP tests (`tests/04_edit_order_and_widening.sql`) covering authorization, pricing, no-op refusal, forced-reapproval, stale-version conflict, and negative-price rejection. **Full suite: 46/46 passing** (up from 37/37 in Phase 8A.5).
- `public/js/orderLifecycle.js` was rewritten as a genuinely async facade — reads stay synchronous over an in-memory cache (same pattern `community.js`/`sites.js` already used), but every write (`createOrder`, `editOrder`, `cancelOrderDirect`, `requestCancellation`, `decideCancellationRequest`, `approveOrder`, `rejectOrder`, `revertApproval`, `startPurchase`, `abandonPurchase`, `completePurchase`, `claimDelivery`, `collectDelivery`, `cancelDelivery`, `deliverOrder`) is now genuinely `async`, calling a `SECURITY DEFINER` RPC. `store.js` and `cancellationRequests.js` — the two standalone modules that used to own this data — were **deleted**, their responsibilities folded into `orderLifecycle.js`. Every write function's signature dropped its old `actorId`/`actorName` parameters — the server now derives the acting user from the real session (`auth.uid()`), rather than trusting a client-supplied id.
- **Real optimistic concurrency**: every order gained an integer `version` column; every write RPC locks the row and checks/increments it, refusing with Postgres error `40001` on a stale write — genuine database-level concurrency control, replacing the old client-side "re-read localStorage before writing" convention. **Verified with genuine two-connection races** (raw `docker exec ... psql`, bypassing pgTAP's single-transaction limitation): a concurrent `start_purchase` race (two buyers) and a concurrent `claim_delivery` race (two drivers) each resolved with exactly one winner and one correctly-refused loser.
- **Buyer hold-to-confirm rewritten as an explicit async state machine** (`idle → starting → holding → completing/abandoning → done`) — the critical property, directly verified: the 3-second countdown never begins until `startPurchase` has actually round-tripped to the server and succeeded, closing a real window where the old code could have shown a countdown for a purchase attempt that hadn't actually been accepted yet.
- **Pricing trust boundary, stated honestly**: `total_price` is server-computed and `unit_price` is server-validated as non-negative, but there is still no real server-side product catalogue — `unit_price` itself remains client-supplied (from the `data.js` mock catalog), so the arithmetic is now trustworthy but the input price is not independently verified. Documented as a deliberate limitation, not fixed this phase (no supplier API/catalogue was built, per explicit scope).
- **A `500` observed mid-testing was investigated and confirmed not a bug**: Postgres's `40001` (serialization_failure, used for the stale-version conflict) surfaces as HTTP `500` through PostgREST's default SQLSTATE-class mapping (class `40` → 500), not 409 as might be expected. `orderLifecycle.js`'s failure handler checks the error code from the response body (`error.code`), not the HTTP status, so the correct refresh behavior fires regardless — confirmed by tracing the exact network log entry back to a deliberate stale-version test.
- **Verified end-to-end**: golden path (create → approve → purchase → claim → collect → deliver); both genuine concurrency races above; edit-forces-reapproval and edit-without-reapproval; direct cancellation; cancellation-request approve and reject; the collect-before-decision auto-close race; a live mid-session permission revocation correctly refused by RLS (not just a stale cache); cross-company isolation; full regression sweep of Owner tabs/detail/timeline, Driver tabs and zero-price rendering, Buyer cancellation panel, notifications, and login/routing — all unchanged in behavior from before the migration. Zero unexplained console/network errors.

### Server-backed notifications (Phase 8D.1)

- **Implemented and verified — migration `0014_notifications_backend.sql` applied to both local and hosted `sitestock-dev`; frontend JS changes complete; not yet committed (see git status at the end of this file's entry).** Closes the last remaining localStorage-only slice: notifications and notification preferences move to the real `notifications`/`notification_preferences` Postgres tables that Phase 8A actually created back in `0007_notifications.sql` but deliberately left unwired ("schema only... nothing writes to this table yet" — that comment is what this phase finally acts on).
- **Two creation paths, matching where the underlying event already happens** — this was the central design decision, made explicitly before writing any SQL: (1) the 12 order-lifecycle notification types are appended *inside* the existing order-lifecycle RPCs (`create_order`, `edit_order`, `approve_order`, `reject_order`, `revert_approval`, `complete_purchase`, `claim_delivery`, `mark_collected`, `mark_delivered`, `cancel_delivery`, `request_cancellation`, `decide_cancellation_request`), in the same transaction as each RPC's own `order_events` insert — content and recipients are computed server-side from the row the RPC itself just validated, never from client input; (2) the 7 non-order types (buyer access grant/revoke/request/reject, site member add/remove, site archive) come from `community.js`/`sites.js`'s pre-existing direct client table writes (never RPCs), so 7 new narrow `notify_*` RPCs were added instead — each independently re-validates the specific claim against real database state (the grant/membership row that write just created, or `is_owner` where that row is already gone by revoke/remove) before writing anything.
- **The actual security gap being closed**: `0007`'s schema had deliberately shipped with no INSERT grant on `notifications` for `authenticated` at all — confirmed still true going into this phase (a direct authenticated INSERT attempt returns `42501` even for a real, legitimate user). This phase's whole job was building the RPC layer that comment always implied would exist. Verified directly, both locally (pgTAP) and against the hosted project (raw curl against the real REST/Auth/RPC API): a stranger cannot INSERT into `notifications` directly, and — for the two `notify_*` RPCs a pre-commit audit actually exercised at the time (`notify_buyer_access_granted`, `notify_site_archived`) — cannot claim credit for a grant/membership change they didn't actually make, both refused with `42501`. *(A stricter self-audit later in this phase found this generalization — "cannot call **any** `notify_*` RPC" — had only actually been tested for 2 of the 7; see the "Pre-commit hardening" entry immediately below for the correction and the now-genuinely-exhaustive coverage.)*
- **`notification_type_enabled_for(userId, type)`** (new SQL function) is the single source of truth for creation-time preference filtering server-side — mirrors the retired client-side `NOTIFICATION_TYPES`/`DEFAULT_PREFS`/`isTypeEnabledFor` mapping exactly (same category/configurable/subKey/defaults), verified directly: turning a recipient's `approvalUpdates` preference off before an order is created means zero `order_awaiting_approval` notification for them, even though the order itself is created successfully.
- **`notifications.js` rewritten** as the same synchronous-facade-over-async-cache pattern every other data module already uses: reads (`getNotificationsFor`, `getUnreadCount`, `getPreferences`) stay synchronous over an in-memory cache refreshed on auth transition/view-entry/window-focus (wired into `main.js`'s existing `refreshDataCaches()`, exactly alongside community/site/order refresh); writes (`markRead`, `markUnread`, `markAllRead`, `savePreferences`) are genuinely `async` now, hitting the tables directly (both already RLS-scoped to `auth.uid()`, so a direct client UPDATE/UPSERT for these specific operations is safe — unlike creation). **The `notifyUsers` export is gone entirely** — `orderLifecycle.js` no longer imports `notifications.js` at all (nothing left for it to do once the RPC call itself already wrote the notification); `community.js`/`sites.js` call the relevant `notify_*` RPC immediately after their own existing write succeeds instead.
- **A real ordering bug was caught and fixed during local frontend verification**: the rewritten `notifications.js` initially declared its cache/refresh section before its pub-sub section, but `subscribeAuth`'s callback fires synchronously and immediately on subscribe — this produced a real `ReferenceError: Cannot access 'listeners' before initialization` on every page load, caught immediately via console inspection and fixed by reordering (pub-sub declared first, matching the ordering rule `orderLifecycle.js`'s own header comment already documents for the identical pattern). Re-verified clean afterward.
- **Verified end-to-end through the real local UI** (not just pgTAP): Owner + Worker accounts, a real community/site, buyer-access grant (`notify_buyer_access_granted`) and site-member-add (`notify_site_member_added`) both produced correct, correctly-worded notifications; a real order created with approval required correctly notified the owner (`order_awaiting_approval`, exact expected message text); approving it correctly notified the buyer (`order_ready_for_purchase`, including correct server-computed `£33.75` price formatting via a new `_format_price` SQL helper matching `data.js`'s `formatPrice` exactly); notification click-through still opens the Phase 6 order-detail view correctly (unchanged, unaffected by this phase); mark-read/mark-all-read both work; Driver and Buyer role views both still render correctly with zero regressions (Driver still shows no prices).
- **Multi-device proof, done properly this phase** (not just sequential login/logout in one tab, which earlier phases used and disclosed as a caveat): two genuinely independent browser tabs, each with their own real Supabase session and in-memory cache. Action in tab A (mark notification read, change a preference) → refresh tab B (a completely separate JS module instance, forced to re-fetch from the server) → tab B correctly shows the update. Repeated against the hosted project too, using raw HTTP requests with zero client-side cache at all (each request is its own fresh "session" by construction) — read-state and preference changes both round-tripped and persisted correctly. **No Realtime involved anywhere** — every proof here is refresh/re-entry-based, exactly per this phase's explicit scope boundary.
- **The full pgTAP suite is 82/82** (61 carried over unchanged + 21 new in `supabase/tests/06_notification_backend.sql`), covering: anon cannot read/write notifications; cross-user notification read/write isolation; a stranger cannot forge a notification via either the raw table or a `notify_*` RPC; preference rows are private and self-service only; a legitimate action produces the correct notification; a retried/duplicate lifecycle call does not create a duplicate notification (the same conditional-`UPDATE`-with-`WHERE`-status guard that already makes order-lifecycle concurrency safe means a retry never even reaches the notification insert a second time); and recipient identity isolation holds even between two users sharing an identical display name.
- **Deliberately not built this phase, per explicit scope**: Supabase Realtime (no `supabase.channel()`, no `postgres_changes` subscriptions — explicitly out of scope, to be considered only after this phase's data layer is accepted), notification pruning/capping (flagged as a known future item, not fixed), and any change to notification *content*/*preference semantics* beyond porting them faithfully server-side.

#### Pre-commit hardening (migration `0015`, same phase)

A strict pre-commit audit run before staging found the overall design sound (no RLS weakening, no privilege escalation, no generic forgery endpoint, no lifecycle scope creep) but surfaced two real, previously-undisclosed gaps, both addressed here without touching `0014` (already applied to hosted — forward-only, per the established migration discipline):
- **Revoke/remove notification-content-integrity gap**: `notify_buyer_access_revoked`/`notify_site_member_removed` could only re-validate "is the caller currently an owner," since the underlying grant/membership row is already deleted by the time a *separate* notify call runs — a real owner could theoretically send a misleading "access removed" notification for someone who was never actually revoked/removed. **Fixed with two new authoritative RPCs, `revoke_buyer_access`/`remove_site_member`** (migration `0015_revoke_remove_notification_integrity.sql`), which perform the deletion *and* the notification in one transaction — the database now proves a real row existed (via Postgres's own `FOUND` check after the `DELETE`) before any notification is possible. `community.js`'s `revokeBuyerAccess`/`sites.js`'s `removeSiteMember` now call these instead of a client-side delete. The two superseded RPCs still exist (unedited) but had their `EXECUTE` grant revoked — permanently unreachable, closing the gap outright.
- **Test-coverage-completeness gap**: only 2 of 7 `notify_*` RPCs and 2 of 12 order-lifecycle notification types had been positively exercised by a real test run (the rest rested on code review alone, despite `PROGRESS.md`'s own earlier wording implying broader coverage — corrected above). **Fixed with a new file, `supabase/tests/07_notification_matrix.sql` (45 new tests)**: legitimate-success + forgery/unauthorized-refusal for all 7 non-order paths (including the new nonexistent-removal case for revoke/remove specifically), plus a genuine 6-order lifecycle progression exercising all 12 order-lifecycle notification types at least once each, asserting correct recipient/type/order-id and no unintended duplicates throughout.
- **Full suite: 127/127** (82 carried over unchanged + 45 new). **Local functional checks** (real UI + direct RPC calls against the live dev-stack session): legitimate revoke/remove both work through the real Team-panel/site-detail UI; a false/nonexistent revoke or removal is refused (`42704`) with no misleading notification; an unauthorized (non-owner) attempt is refused (`42501`) with the real grant/membership left untouched. **Hosted**: migration `0015` applied to `sitestock-dev` (parity re-confirmed 0001–0015 local ⇄ hosted), then the identical A–F matrix re-proven via raw HTTP against the real REST/RPC API, plus spot-checks confirming raw-insert forgery is still refused, anon still cannot call the protected RPCs, cross-user notification reads stay isolated, and both superseded RPCs are confirmed unreachable even for a genuine owner.
- **Frontend regression**: grant/add-member, role switching, Community→Sites, Worker ordering, order notifications, and Driver's zero-price rendering were all re-confirmed working through the live UI in the same session as the revoke/remove checks above — no regressions from routing these two mutations through the new RPCs.

### Realtime freshness layer (Phase 8D.2) — local, hosted, and real-device verified — CLOSED

- **Implemented and verified against the local Supabase stack, hosted `sitestock-dev`, and a genuine second-physical-device (PC + phone) acceptance test — all three passed.** Migration `0016` applied to both backends, full test matrix re-run and passed on hosted (see the dedicated hosted-verification entry below). Phase 8D.2 is closed.
- **Physical acceptance test (real PC + real phone, no automation)**: Test 1 (Worker order on phone → Owner PC updates automatically) PASS. Test 2 (notifications update automatically) PASS. Test 3 (Buyer access revocation updates/routes correctly) PASS. Test 4 (site-membership removal invalidating an already-selected site) initially **FAILED** on first physical attempt, then PASSED after the fix below.
- **Test 4 root cause**: `public/js/site.js`'s `subscribeSites` reactive handler only ever re-rendered the site *picker's* list, and only while the Worker was actually sitting on the picker screen (`siteSelectPanel` visible) — the case the earlier local multi-tab verification covered, and it worked. It never looked at `selectedSite`, the variable holding a site the Worker had already chosen and was actively ordering against on the search/order-form screens (picker hidden). So a membership removal that happened while the Worker was genuinely *inside* a site had nothing reacting to it — exactly the gap the automated local/hosted passes hadn't exercised, and exactly what the real phone caught.
- **Test 4 fix**: `subscribeSites`'s handler now additionally checks, on every authoritative refreshed sites cache (never the raw Realtime payload — it re-derives from `getActiveSitesForUser()` against the already-refreshed cache), whether the Worker's current `selectedSite` is still in their real authorized list. If not, it calls the existing `refreshWorkerView()` (the same full reset `main.js` already uses on ordinary view-entry) to close any open order/edit context and return the Worker to a freshly re-derived site-selection screen — which itself already shows the pre-existing "you haven't been assigned to a site yet" message when none remain. This was always a UI-freshness gap, never a security one: `createOrder`'s/`editOrder`'s own independent server-side `canCreateOrderForSite` re-check was never bypassable and stayed untouched.
- **Retest before the physical pass**: reproduced the bug on the unfixed code first (`git stash`), confirmed the stale site context persisted with zero console errors after a real membership removal; restored the fix and confirmed the Worker's screen automatically left the site context with no refresh — both locally and, separately, against hosted `sitestock-dev` (via the documented temporary, uncommitted `env.js` override, reverted before finishing — confirmed via empty `git diff`). Re-ran the original picker-visible scenario too, confirming no regression. Full pgTAP suite unaffected (**144/144** — this fix is frontend-only, no migration or RLS change).
- The user then repeated Test 4 on the real PC + real phone against the verified fix artifact, without any manual refresh, and confirmed it passed.
- **Architecture, approved before implementation**: Realtime is a freshness *signal* only, never a new source of truth. Every `postgres_changes` event calls the exact same authoritative `refreshXCache()` function view-entry/focus refresh already used — event payloads are never applied directly to any cache. Two channels per session: a user-scoped one (`notifications`, filtered `recipient_user_id=eq.<userId>`) and a community-scoped one (`orders`, `cancellation_requests`, `sites`, `site_memberships`, `community_memberships`, `owner_grants`, `buyer_grants`, `buyer_requests`, `communities`, filtered `community_id=eq.<activeCommunityId>`), both orchestrated by the new `public/js/realtime.js` — `startRealtimeForSession()`/`stopRealtime()`/`reinitializeRealtimeForCommunity()`, wired into `main.js`'s bootstrap/`sitestock:logged-in`/`sitestock:logout` handlers. `order_events`/`profiles`/`notification_preferences` deliberately excluded (see that file's and `0016`'s headers for why).
- **Migration `0016_realtime_publication.sql`**: adds the ten approved tables to the `supabase_realtime` publication via an idempotent `DO` block. Publication-audit-before-writing confirmed both local and hosted `sitestock-dev` had zero tables in the publication beforehand — clean slate, no drift.
- **A real bug was found and fixed during this phase's own local verification, not assumed away**: a live test revoked a Worker's `buyer_grants` row (a real `DELETE`, via the existing `revoke_buyer_access` RPC) while that Worker's Buyer view sat open, idle, in a separate browser tab. The event never arrived — zero errors, just silent staleness. Root cause: under Postgres's default `REPLICA IDENTITY`, a `DELETE`'s WAL entry carries only primary-key columns, so a channel filter on `community_id` (not the primary key) can never match a `DELETE` event — Realtime drops it rather than delivering or erroring. A control test (an `INSERT` with the same filter) propagated correctly within seconds, isolating the gap to `DELETE` specifically. **Fix**: `REPLICA IDENTITY FULL` on exactly the three tables anywhere in this codebase where a row is ever genuinely deleted rather than status-updated — `owner_grants`, `buyer_grants`, `site_memberships` (found by grepping every migration file and every client-side `.delete(` call site) — added to `0016`, not a new migration, since `0016` hadn't been applied to hosted yet. Reached from `pending_approval`, `pending_purchase`, `purchased`, or `claimed`, all through one shared `cancel_order` action key in `orderLifecycle.js`'s `TRANSITIONS` table, so the state machine doesn't fork into two cancelled flavours. No entry at `collected`/`delivered` — deliberate, see below.
- **`editOrder(orderId, fields, actorId, actorName)`** — a Worker can directly edit their own order (`requestedById` re-checked fresh, no Owner override this phase) whenever nothing's been signed off yet (`pending_approval`, or `pending_purchase` with `approvedById` still null — i.e. approval was off). If a real Owner approval already happened, editing is still allowed but automatically resets the order to `pending_approval` and clears the approval fields in the same action (reusing the existing revert edge, Worker-triggered) — an edited order can never silently survive as the version the Owner actually approved. Refused outright at `purchase_in_progress` (fail-safe, retryable) and everything `purchased`-and-beyond. Only a fixed field whitelist is ever accepted from the caller; a `siteId` change is re-authorized exactly like order creation (`canCreateOrderForSite`, active-site check, community match) and re-snapshots the new site's fields fresh, never trusting caller-supplied text.
- **`cancelOrderDirect(orderId, actorId, actorName, reason)`** — instant Worker cancel, legal at `pending_approval`/`pending_purchase` regardless of approval status (the boundary is money spent, not approval sign-off). Refused with a specific, retryable message during `purchase_in_progress`.
- **Post-purchase cancellation is a request, not a direct action** — `requestCancellation`/`decideCancellationRequest`, legal at `purchased`/`claimed` only, blocked from `collected` onward (the goods are physically with the driver by then, and approving a cancellation would need a way to tell them to stop, deliberately out of scope this phase). New module `cancellationRequests.js` (`sitestock_cancellation_requests_v1`) follows the exact shape `community.js` already established twice for join/buyer requests — own storage key, own pub-sub, one pending request per order. `order.status` is left completely untouched while a request is pending, so a Driver can still claim/collect normally — **verified directly**: a request created before a claim didn't block the claim, and the Buyer's later approval still succeeded correctly afterward.
- **Race conditions verified deterministically**: a Driver collecting the order before the Buyer decides makes the approval attempt fail *at the TRANSITIONS table itself* (no `cancel_order` edge at `collected`) — the request is then automatically closed as `rejected` with a system-generated reason rather than left dangling as `pending` forever, and the order is confirmed to remain exactly at `collected`, never silently cancelled out from under a physically-collected delivery. Deciding an already-decided request a second time is refused. A Buyer whose access was revoked mid-flight can no longer decide; a still-valid Buyer for the same site still can.
- Approving a request while `claimed` clears `driver`/`driverId`/`claimedAt` on the order (mirroring the Driver's own existing `cancelDelivery`) while preserving the departing driver's identity in the `order_cancelled` event's `meta` — and the assigned driver is added as a recipient of the same `cancellation_approved` notification the Worker gets, since they'd otherwise have no way to learn the thing they claimed is no longer needed.
- **Minimum event set, exactly four new types**: `order_edited` (carries a structured `meta.changes` diff — only fields that actually changed), `order_cancelled` (used for *both* the direct-cancel and approved-request paths, distinguished by `meta.via`, not split into two types), `cancellation_requested`, `cancellation_rejected` (also covers the automatic race-condition close-out). No separate `cancellation_approved` *event* — the approved outcome is already fully captured by `order_cancelled`; `cancellation_approved` exists only as a notification type. An edit that forces re-approval logs **two** events from one transition (`order_edited` + the reused `approval_reverted` type) — the same multi-event-per-transition shape `cancelDelivery` already uses — and never touches the original `approved` event from when the Owner first signed off.
- Four new, additive, nullable order fields — `orderCancelledBy`/`orderCancelledById`/`orderCancelledAt`/`orderCancellationReason` — deliberately named distinctly from the pre-existing `cancelledBy`/`cancelledById`/`cancelledAt`/`cancellationReason`, which mean something different (a Driver dropping their own delivery claim, order stays alive). **No `sitestock_orders_v4` version bump** — everything new is additive, matching the precedent already set for `requireOwnerApproval` and `siteId`.
- **Verified directly** across four groups exactly as specified before implementation: edit rules (11 cases — own order at every eligible/ineligible status, another worker's order, cross-community site, unauthorized site, no-op edit), direct cancel (7 cases), cancellation requests (7 cases, including the collected/delivered cutoff and duplicate-request refusal), and Buyer decisions (14 cases, including the full race-condition matrix) — every single one passed. Identity/security re-verified separately: identical display names with different ids stayed isolated, a never-approved "ghost" user was refused, cross-community actors were refused, a revoked buyer lost decision authority while a still-valid one retained it. Confirmed via the real UI that the new `cancelled` status and edited orders render correctly through the **unmodified** Phase 5 owner dashboard/tabs (new event types fall back to the existing generic `{icon: '•', text: ...}` rendering without any `owner.js` changes; `cancelled` orders don't appear in any existing tab, nor leak into the wrong one — expected, since the "Cancelled" tab itself is deferred). Zero console errors throughout.
- **Deliberately not built this phase**: any UI at all (Worker edit/cancel buttons, Buyer decision screen, Owner "Cancelled" tab), Owner edit-on-worker's-behalf, cancellation after collection/delivery, a "reason for ordering" field, supplier refunds/returns, and everything else explicitly listed out of scope in the approved architecture plan.

## Architectural decisions worth remembering

- **Why a custom `dev_server.py` instead of `python -m http.server`**: the plain stdlib server caused a real, reproducible bug — edited files served stale via browser conditional-GET caching within the same second as the edit. `dev_server.py` sends `Cache-Control: no-store` on everything to guarantee fresh content during active development.
- **Why owner access is resolved dynamically (`isOwner = isCreator || hasOwnerGrant`) rather than a fixed role field on the community/account**: the user wanted a real permission model — "only the creator is the owner unless someone else is given access" — not a cosmetic label. This also made the later "auto-resolve role at community entry" feature straightforward, since the same `isOwner` check just gets consulted at a different point in the flow.
- **Why the revert lock triggers at `picked_up`, not `delivered`**: user-directed correction — the real point of no return is when the driver has physically collected goods from the supplier, not whenever the driver later marks final delivery complete.
- **Why signup asks the role question once instead of every community visit**: explicit user direction to stop the repeated "Choose your role" prompt; the account now carries a `defaultRole` used to auto-resolve on every community entry, with owner status never overridden by a stale/aspirational preference.
- **Why stockist links go to homepages, not deep product links**: we don't have real product-page URLs for the mock catalog, and guessing one would be actively misleading. The confirm screen is explicit about this ("Opens their homepage in a new tab — this is a demo catalog...").
- **Why `dev_server.py` reads `PORT` from the environment and `launch.json` has `autoPort: true`**: this project can end up open in more than one chat session at once (e.g. the user working from a new chat while an old one is still around), and the second session can't bind port 3000. Auto-picking a free port means a second session still works instead of failing outright — just don't assume the preview is always at `localhost:3000`, use whatever the `preview_start` tool reports.
