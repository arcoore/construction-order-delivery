## Completed features

### Core ordering flow
- Mock catalog search (materials/tools/PPE), two-step "pick material → pick size" flow with a "custom size" escape hatch, quantity + delivery postcode.
- Worker chooses *which stockist to buy from* (not the driver) — sees a list of carrying branches with a live-ish pickup-availability estimate, a confirm screen with a real link to that stockist's real homepage (not a fabricated deep link — explicitly scoped down from "give them an Amazon link" per user direction), then places the order.
- Driver view: browser geolocation (with manual-postcode fallback if denied), Requests/My Deliveries/Completed tabs, distance-sorted pickup list, claim → collect → deliver, with a cancel-and-return-to-pool path (see Phase 2A below).
- Pricing shown to Worker (own orders), Owner (dashboard), and Buyer (review screen) — **never to Driver**, closing a bug the Phase 1 audit flagged.

### Order lifecycle & Buyer role (Phase 2A)
- Full rework of the order state machine and history, planned in a dedicated architecture pass before any code changed (state machine, event schema, permission rules, data changes, reuse/replace inventory, edge cases, implementation order — all agreed before implementation started).
- New `orderLifecycle.js` is now the *only* place allowed to change an order's status — every action (`approveOrder`/`rejectOrder`/`revertApproval`/`startPurchase`/`abandonPurchase`/`completePurchase`/`claimDelivery`/`collectDelivery`/`cancelDelivery`/`deliverOrder`) re-reads the order fresh, validates the transition against a `TRANSITIONS` table, and refuses anything not explicitly listed — invalid transitions are refused at the data layer now, not just hidden by which button got rendered.
- New status flow: `pending_approval → pending_purchase → purchase_in_progress → purchased → claimed → collected → delivered`, with `rejected` off `pending_approval` and `approval_reverted` back from `pending_purchase`/`rejected`. Owner approval is now **configurable per community** (toggle in the owner dashboard) — orders skip straight to `pending_purchase` when it's off. Each order snapshots `approvalWasRequired` at creation so changing the setting later never reinterprets existing orders.
- New append-only event log (`sitestock_order_events_v1`, via `orderLifecycle.js`) — every transition appends an event (actor id + display-name snapshot, from/to status, reason, timestamp); no update/delete function is ever exported, so history can't be edited in normal operation. The owner dashboard's "Recent activity" feed now queries this log directly instead of reconstructing history from mutable order fields — **verified a revert no longer erases the approval event that preceded it**, fixing the exact bug the Phase 1 audit flagged.
- New **Buyer** role, **owner-granted only** (not automatic like worker/driver, since it handles real purchasing) — members request it from their Profile screen, any owner can approve/decline the request or grant it directly from the Team panel. Buyer reviews the full order (with cost), then must **press and hold "Purchased" for a real 3 seconds** — verified this is a genuine timer, not a fake progress bar (a hold that was never released completed only after 3 real seconds had actually elapsed). Releasing early correctly abandons back to `pending_purchase`.
- Driver can now **cancel** a claimed delivery (reason required) — it returns to the pool (`purchased`) for another driver to claim; verified the departing driver's identity is preserved in the event's `meta` even though the order's own `driver`/`driverId` fields get cleared — this is exactly what the Phase 3A `delivery_cancelled` notification (see below) uses to tell the buyer who dropped it and why.
- Both the buyer-purchase hold and driver-claim are guarded against double-action races (two people going for the same order) by always re-reading localStorage fresh before writing — verified directly: a second claim/purchase attempt on an already-taken order is refused with a clear error, not silently overwritten.
- Orders bumped to `sitestock_orders_v3` (old `_v2` test data intentionally discarded, not migrated, per explicit direction).

### In-app notification centre (Phase 3A)
- Planned as a full architecture pass before any code changed (data model, event→recipient matrix for all 19 candidate events, role-based content rules, read/unread model, preferences model, storage/subscription design, navigation/deep-link design, security rules, edge cases) — approved with specific decisions on defaults, preference filtering timing, and non-configurable types before implementation started.
- New `notifications.js` owns `sitestock_notifications_v1` + `sitestock_notification_prefs_v1`. `recipientUserId` is the only field used for ownership/routing — never a display name. Recipients are computed by `orderLifecycle.js`/`community.js` using `community.js`'s own permission functions (`getOwnerIds`, `getBuyerIds`, `approvedMembers` — the first two are new).
- 13 real notification types, wired into every relevant `orderLifecycle.js` action and into `community.js`'s buyer-role functions (request/grant/decline/revoke). Several of the original 19 candidate events (`purchase_started`, `purchase_abandoned`, `purchased`, `delivery_returned_to_pool`) deliberately produce **no** notification — consolidated into their more meaningful neighbor or judged not worth a push.
- **Creation-time preference filtering** — verified directly: with a category/sub-switch off, an event produces zero notification rows for that recipient; turning it back on afterward does not retroactively create what was missed.
- **Self-notification suppression** — verified directly: a user who is both the actor and technically an eligible recipient (e.g. a buyer who's also an approved "driver-pool" member) never receives a notification about their own action, even with the relevant preference explicitly turned on.
- **Content is generated role-appropriately at creation time** — verified the driver-facing `delivery_available` message contains no price anywhere in the stored string (not just hidden by CSS later).
- **Click-through re-checks permissions live** — verified the important case directly: revoked a user's buyer access, then clicked their still-unread "you've been granted buyer access" notification; it correctly fell back to their legitimate view instead of opening the buyer screen. A notification's stored `navigationTarget` is a suggestion, never an authority.
- **Identical display names stay fully isolated** — verified with two different accounts both named "Same Name": zero overlapping notification ids, every notification's `recipientUserId` matches its actual owner, "mark all as read" for one never touches the other's unread count.
- **Cross-tab updates confirmed live** (native `storage` event, no polling) — a notification created in one tab appeared in another tab's badge without a reload.
- Bell + dropdown panel (topbar, visible whenever authenticated — not just inside a role-view) reusing the existing account-menu dropdown pattern; global unread badge across all the user's communities, not just the active one; mark read/unread per row; mark all as read (scoped to the current user by construction).
- Preferences modal: 4 category presets (Order/Approval/Delivery/Role updates) + 3 sub-switches under Delivery updates (the three types whose sensible default disagrees with the category's own default) + one Save Changes / Cancel pair, holding a local draft until Save — verified Cancel discards changes and Save persists them.
- `buyer_access_granted`/`buyer_access_revoked` are non-configurable (always fire) since they directly affect the recipient's own permissions; everything else respects preferences.
- **Known, deliberately-unsolved consideration**: `sitestock_notifications_v1` only grows, no pruning yet — flagged in CLAUDE.md as a future item, not fixed now since nobody's asked for it.

### Sites / Projects (Phase 4A)
- Planned as a full architecture pass before any code changed (data model, membership model, permission model, order↔site relationship, historical-snapshot strategy, archive-vs-delete recommendation, storage-versioning recommendation, UI/navigation, edge-case handling) — approved with specific decisions (clean `_v4` reset of orders, "Sites" as the domain term with the existing `site.js` Worker view left unrenamed, `deliveryInstructions` as an optional site field) before implementation started.
- New `sites.js` module: a **Site** (job location, e.g. "24 High Street") belongs to exactly one community; a company can have many. Many-to-many site membership (`sitestock_site_memberships_v1`) — an employee can be assigned to zero, one, or many sites, following the exact `community.js`/`store.js` module pattern (own storage keys, own pub-sub, owner-only mutating functions that re-check permission fresh).
- New permission composites (`canManageSite`, `canAccessSite`, `canCreateOrderForSite`, `canPurchaseForSite`) are the single place site access is decided — role checks (worker/buyer) and site membership are always ANDed together, owner always bypasses both, and every composite independently re-derives the site's real `communityId` before trusting membership. **This last check exists because of a real bug caught during this session's own verification**: without it, a user's membership in one company's site could satisfy a permission check mistakenly scoped to a different company if a caller ever passed a mismatched `communityId` — found via a direct cross-community test, fixed at the module boundary, and re-verified before shipping (see CLAUDE.md's "Site model" section for the detail).
- `orderLifecycle.js`'s `createOrder` now independently authorizes the site (`canCreateOrderForSite`) before writing anything, and refuses orders against an archived site — a worker cannot create an order for a site they aren't assigned to no matter what the UI renders, closing the exact "reference is not permission" gap the brief called for. `startPurchase` got the equivalent `canPurchaseForSite` check.
- Every order now permanently snapshots `siteId` + `siteName`/`siteAddress`/`sitePostcode`/`siteDeliveryInstructions` at creation time (same `*Id` + display-snapshot convention already used for `requestedBy`/`driver`/`approvedBy`) — **verified directly**: renamed a site after an order existed, and the order's own card/history still read the old name everywhere, while the live site record and any *new* order picked up the new one.
- Orders bumped to `sitestock_orders_v4` — a clean reset (old `_v3` local test data intentionally discarded, matching the precedent of every prior structural order-shape change), so `siteId` is a required field with no "legacy/unassigned site" branching anywhere in the UI.
- New owner-only `sitesView.js` screen (reached via a "Sites" topbar pill, visible only in the owner role): list of active/archived sites with a tab toggle, create-site form (name/address/postcode/optional delivery instructions), and a site detail view (info with inline edit, employee assign/remove list drawn from `approvedMembers`, and the site's own order list) — archive/restore in place of any permanent-delete function, per the explicit "archive, don't delete" decision.
- Worker's `site.js` order wizard gained a mandatory **site-selection step 0**, sourced from `getActiveSitesForUser` (active sites the worker is actually assigned to) — a worker with zero site assignments sees a blocking message instead of the search panel, and the postcode field is pre-filled (but still editable) from the chosen site's postcode as a small usability nicety. **Verified directly**: a worker assigned to only one of two sites in a community saw only that one site in the picker, and a direct data-layer bypass attempt to create an order against the other site was refused.
- `buyer.js`'s purchase queue now filters every order through `canPurchaseForSite`, not just `isBuyer` — **verified directly**: a buyer granted access to Site A but not Site B saw Site A's pending-purchase order but not Site B's (seeded directly to isolate the check), and a direct `startPurchase` bypass attempt on the Site B order was refused.
- `driver.js`'s delivery cards now show the order's snapshotted site name/address/postcode/delivery-instructions instead of just a raw postcode — **verified no price is present anywhere on a driver's card**, matching the existing "drivers never see unitPrice/totalPrice" rule. `owner.js`'s order cards and `site.js`'s/`buyer.js`'s own history/list items also now show the site name for context.
- **Verified end-to-end** in the browser: owner created two sites, assigned a worker to one, the worker placed an order visible only through that site's picker, the owner approved it (dashboard order card showed the site), a buyer authorized for that site purchased it, a driver claimed/collected/delivered it seeing site info but no price — archiving the site mid-flow (after purchase, before delivery) had zero effect on completing the delivery, exactly as designed. No console errors from any Phase 4A code across the whole flow.
- **Deliberately not built this phase** (per explicit scope): site-aware notifications (architecture left compatible — `notifyUsers`'s payload would need `siteId` added to its fixed destructure, a small non-breaking future change, not done now), messaging, budgets/spending controls beyond what already existed, supplier APIs, maps/GPS/geocoding for sites, photo proof, a site-manager role, site analytics beyond the basic summary counts already in the list/detail views, and permanent site deletion.

### Delivery completion details (Phase 2B)
- `collected → delivered` now requires the driver to fill in a required delivery time (`deliveryTime`, datetime-local input) and delivery location (`deliveryLocation`, free text pre-filled with the order's postcode) before confirming — enforced both client-side and inside `orderLifecycle.js`'s `deliverOrder`, so it can't be bypassed. No photo proof — deliberately kept out of scope.
- `deliveredAt` (automatic system timestamp of confirmation) and `deliveryTime` (driver-reported) are kept as two distinct fields on purpose, since they can differ.
- The `delivered` event now carries `meta: { deliveryTime, deliveryLocation }` alongside the existing actor id/display-name snapshot.
- Owner's order cards and activity feed, and the worker's own order history, all show the confirmed delivery location/time; verified pre-existing delivered orders (created before this change, with no location/time) degrade gracefully rather than showing broken text.

### Approval workflow
- Owner approve/reject UI with inline reject-reason form (now via `orderLifecycle.js`, see above).
- 72-hour revert window on approve/reject decisions, live countdown, locks permanently once `purchased` (moved earlier than the old `picked_up` lock — once a buyer has actually spent money, reverting the *approval* doesn't make sense, so the window now closes at that point instead).
- Owner Dashboard: 6 stat tiles (members, pending join requests, awaiting approval, out for delivery, delivered, total spend — now summed from `purchasedAt`, not order status) + a real event-log activity feed (see above).

### Communities (Discord-style, multi-tenant)
- Owner creates a community (gets a generated invite code); Workers/Drivers join either by code or by browsing a searchable list — **join is a request, not instant**, gated by owner approval (mirrors the order-approval UX intentionally).
- Everything (orders, dashboard stats, requests) is scoped by `communityId`. Verified two separate communities don't leak data into each other.
- Owner-only "Team" panel: grant/revoke owner-level access to any approved member. Granting fires a one-time "You've been upgraded to owner level" popup the next time that person's identity is active, then drops them straight onto the dashboard. Access is always `isCreator || hasOwnerGrant` — a granted owner cannot themselves grant further (only the true creator sees the Team panel).

### Identity foundation (Phase 1 of post-audit work)
- A full read-only product audit was done first (all screens/workflows checked against code, not assumed from the UI) — see the audit artifact from that session for the complete findings. It surfaced that permissions/ownership/order-attribution were all resolved by a free-text display-name string, not a stable id — meaning in "Skip for now" mode, typing an existing owner's exact name instantly granted their owner access, no password needed.
- Fixed as Phase 1, foundation-only (no new roles/features): new `identity.js` module resolves "who is the current user" as a stable `userId` — `account.id` for real accounts, a persisted random guest id for "Skip for now" sessions. Display names are now purely cosmetic labels attached to that id; typing a name can never grant someone else's access.
- `community.js` (ownership, membership, join requests, owner grants) and `store.js` orders (`requestedById`/`driverId`/`approvedById`/`rejectedById`) now key all permission/ownership logic off `userId`, never a name. Historical display names are kept as separate snapshot fields so order cards/activity feeds still read correctly.
- Driver's "My Deliveries"/"Completed" filters now match by `driverId`, not display name — verified two guests with the identical display name ("Driver Dan") stay fully separate, one never sees the other's deliveries.
- Logged-in accounts get a read-only identity field (sourced from `account.displayName`); only guests can edit their label. Logging out rotates the guest id only when a guest was the one logging out — logging out of a real account leaves a dormant guest identity untouched.
- Storage keys bumped to `_v2` for communities/join-requests/owner-grants/orders (old `_v1` local test data intentionally discarded, not migrated — there was no reliable id to migrate from).

## Architectural decisions worth remembering

- **Why a custom `dev_server.py` instead of `python -m http.server`**: the plain stdlib server caused a real, reproducible bug — edited files served stale via browser conditional-GET caching within the same second as the edit. `dev_server.py` sends `Cache-Control: no-store` on everything to guarantee fresh content during active development.
- **Why owner access is resolved dynamically (`isOwner = isCreator || hasOwnerGrant`) rather than a fixed role field on the community/account**: the user wanted a real permission model — "only the creator is the owner unless someone else is given access" — not a cosmetic label. This also made the later "auto-resolve role at community entry" feature straightforward, since the same `isOwner` check just gets consulted at a different point in the flow.
- **Why the revert lock triggers at `picked_up`, not `delivered`**: user-directed correction — the real point of no return is when the driver has physically collected goods from the supplier, not whenever the driver later marks final delivery complete.
- **Why signup asks the role question once instead of every community visit**: explicit user direction to stop the repeated "Choose your role" prompt; the account now carries a `defaultRole` used to auto-resolve on every community entry, with owner status never overridden by a stale/aspirational preference.
- **Why stockist links go to homepages, not deep product links**: we don't have real product-page URLs for the mock catalog, and guessing one would be actively misleading. The confirm screen is explicit about this ("Opens their homepage in a new tab — this is a demo catalog...").
- **Why `dev_server.py` reads `PORT` from the environment and `launch.json` has `autoPort: true`**: this project can end up open in more than one chat session at once (e.g. the user working from a new chat while an old one is still around), and the second session can't bind port 3000. Auto-picking a free port means a second session still works instead of failing outright — just don't assume the preview is always at `localhost:3000`, use whatever the `preview_start` tool reports.
